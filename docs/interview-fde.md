## 1. 岗位在招什么人

FDE 的日常：进到客户的环境里，弄清客户真正的问题，把产品接进客户已有的系统，部署上线，出问题现场排查，
再把客户的需求反馈给产品团队。**面试官看的不是你会写多少代码，而是下面五件事：**

| 他想确认的 | 你的项目里对应的证据 |
|---|---|
| 能把模糊需求问清楚 | 技能只让管理员维护、"一次连接多项能力"、拒答策略——都是先想清楚"谁在用、怕什么"再做取舍 |
| 会把产品接进客户已有系统 | 企业接口连接器（故事 G） |
| 能独立部署、排障 | Docker Compose 全套、启动配置校验、上线后验证步骤、你自己排过的问题（故事 A、B、J） |
| 有安全和合规意识（客户最在意） | 数据隔离、SSRF 防护、脚本沙箱、短信防刷、限流、Key 加密存储 |
| 测试、数据治理、交付的实战经验 | 空库才暴露的 bug、发布后旧页面白屏、会话续期、首次部署自动建企业、数据体检、数据保留期限、技能中心是空的（故事 M～S） |
| 沟通清楚、不甩锅、敢承认边界 | 每个故事都带"还剩什么没做" |

## 2. 开场

### 30 秒（电梯版）
> 我做了一个多用户的 AI 智能体平台，已经部署在阿里云上。用户配好自己的大模型 Key，建一个助手，挂上知识库和工具就能对话，
> 回答会标明来源，找不到资料就拒答。我花功夫最多的是"能不能放心交给客户用"这一面：数据隔离、成本控制、安全防护和部署。

### 60 秒（标准版）
> 这是一个多用户的 AI 智能体平台，前端 Vue3，后端 FastAPI，MySQL、Redis、ChromaDB，用 Docker Compose 部署在阿里云 ECS 上，域名已经解析。
> 用户带自己的模型 Key，建助手，绑知识库和工具，对话是流式的，每一步——思考、调用工具、检索——都能看到。
>
> 我最想讲的是"怎么让它能交付给客户"：企业接口连接器让助手能查客户已有的系统，但网址和认证由管理员配置，模型没有传网址的能力；
> 额度在调用模型之前检查，不会白花钱；生产环境启动时检查配置，示例密码、弱密码直接拒绝启动；数据按用户隔离，有真实路由级测试证明。
> 上线之后我也处理过一些部署层面的问题，比如限流在 nginx 后面的真实 IP、线上和本地数据库不一致导致技能商店是空的。

### 3 分钟（面试官说"详细讲讲"时）
按这个顺序，每段一两句，**讲完停下来让对方选方向**：

1. **要解决什么问题**（20 秒）：企业想用 AI，但怕三件事——答错、数据串、成本失控。我的设计围绕这三件事。
2. **一次对话的旅程**（60 秒）：前端 SSE → 路由层三道关（限流、额度、并发）→ 业务层拼提示词（助手设定 + 知识库检索结果带来源编号 + 记忆 + 技能）→
   推理引擎循环（思考→调工具→再思考，最多 5 轮）→ 每一步推给前端 → 保存消息、记用量、超阈值提醒。
3. **三个"可信"设计**（60 秒）：
   - 答得准：检索带来源、分数低就拒答，编号类字符串单独做关键词补充召回；
   - 数据不串：所有取数据走统一入口，取不到就当不存在，跨用户访问一律 404，有真实路由测试；
   - 成本可控：额度先检查、限流、并发上限、全站短信封顶。
4. **交付面**（30 秒）：Docker Compose、备份脚本、启动配置校验、发布检查脚本、上线验证步骤。
5. **诚实的边界**（10 秒）：目前是单机小规模上线；没有"公司"级租户隔离；脚本沙箱默认关闭，容器隔离还没在实机验收。

## 3. 十九个项目故事

每个故事用同一个结构：**问题 → 我怎么判断 → 做法 → 结果 → 还剩什么**。面试时每个控制在 1～2 分钟，选跟对方问题最相关的讲。
**文件名都是仓库里真实存在的，被追问时可以直接打开。**

### A. 上线后技能商店是空的（环境差异）
- **现象**：本地导入了 75 个技能，线上商店一个都没有。
- **判断**：线上和本地是两套独立数据库，本地导入的数据不会出现在线上，不是代码 bug。先确认原因，避免瞎改代码。
- **做法**：写了服务器端导入脚本 `scripts/import_skill_pack.py`（`--admin --public --replace`），并保留页面导入方式，文档写清两种方法各自适用场景。
- **FDE 视角**：客户环境和开发环境的数据不同步，是交付里最常见的一类问题。
- **还剩**：线上以前由普通用户创建的旧技能，现在管理员能在后台统一维护，但还没做批量清理脚本。

### B. 限流在 nginx 后面可能失效（部署层的坑）
- **发现**：复盘代码时注意到，限流用 `request.client.host`；经 nginx 再进 Docker，后端看到的是网关地址，所有用户会共用一份额度。
- **诚实说明**：这是**分析代码和部署结构发现的风险**，不是线上已经出过事故。别说成"线上事故"。
- **方案对比**：① `FORWARDED_ALLOW_IPS=*` + 改 nginx——要两处配置都对，漏一处用户就能伪造 IP；
  ② 只信任内网网段，从右往左取第一个非内网地址——nginx 不用改，用户伪造的在左边取不到。选②。
- **落地**：`Dockerfile`，`tests/test_client_ip_proxy.py`（直连 / 两层代理 / 伪造 / IPv6，并且直接读 Dockerfile 里的取值，改坏会被测出来）；
  生产环境设成 `*` 时启动自检会警告（`service/config_validation.py`）。
- **还剩**：线上要重新构建镜像并用 Redis key 验证真实 IP（文档 `docs/deployment.md` 有命令）。

### C. 短信验证码防刷（成本与滥用）
- **现状**：已有每号码、每 IP 的限制；我逐项检查后发现 4 个缺口：全站没有总量上限（换号码换 IP 就能刷）；注册发码在查库前没限流
  （对已注册号码可无限探测）；重置密码提交没有 IP 限流；验证码"错误次数"先读后写，并发请求能绕过。
- **做法**：全站小时 / 天上限；查库前限流；校验按手机号做原子计数（Redis INCR）；发送顺序改成先 IP 后号码，
  被封的 IP 不能占用别人号码的 60 秒冷却。见 `service/phone_verification_service.py`、`FasdtApi/login.py`。
- **诚实说明**：默认阈值是按小规模站点估的，文档写了要按实际用户量调；除非真被刷过，不要说"被攻击过"。
- **FDE 视角**：客户一定会问"被刷了谁买单"。

### D. 技能脚本沙箱（信任边界的取舍）
- **问题**：想直接用网上现成的技能，但技能带脚本，等于让服务器执行陌生人的代码。
- **取舍**：独立容器（无外网、无密钥、只读文件系统、非 root、资源上限）；**默认关闭**；只有管理员导入并审核过的才能运行；
  导入时静态检查脚本，商店里提前标"可运行 / 部分可运行 / 暂不支持"；再加一层网关（`sandbox/gateway.py`），
  让 API 不在沙箱网络里，堵住"脚本反过来访问 API"的缺口；每用户限速、审计日志、附件配额。
- **诚实边界（主动说）**：容器层面的隔离**还没在真实 Docker 上跑过验收**；我写了一键验收脚本 `scripts/sandbox_acceptance.py`，
  部署后要先跑通再对外开。主动承认比被问出来可信得多。

### E. 额度在调用模型之前拦（成本控制）
- **问题**：用户超额了才发现，钱已经花出去了。
- **做法**：`quota_service.enforce_quota_async` 放在聊天路由里、真正调用模型**之前**，超额直接 429；
  用量跨过 80% / 95% / 100% 时推一条提醒（只在"上次没到、这次到了"那一刻推一次，不刷屏）。
- **取舍**：范围有意只做"每月 Token"一种资源，Agent 数、空间数等维度留待客户真的需要时再加。
- **追问**：为什么是 Token 而不是次数？→ 成本和 Token 成正比，次数不反映真实开销。

### F. 回答要可信：来源引用 + 拒答（AI 的可靠性）
- **问题**：企业场景里"瞎编"比"不知道"更危险。
- **做法**：`service/rag/space_search.py::search_spaces`：先校验权限 → 向量化 → 逐个空间检索 → 过滤已禁用文档 → 可选重排序 →
  组装带 `【来源N】` 的上下文 → 命中太少或分数低于阈值（`RAG_MIN_SCORE` 默认 0.2）就拒答；
  合同编号、型号这类精确字符串，向量检索不敏感，所以单独做关键词补充召回。
- **验证手段**：知识库调试台（跑一次检索看命中片段和回答）、健康报告（失败率 / 命中率 / 拒答率 / 引用率）、评估集回归（`docs/evaluation.md`）。
- **还剩**：阈值是经验值，换客户的资料要重新调；这也是 FDE 现场要做的事。

### G. 企业接口连接器（FDE 最对口）
- **问题**：让助手查客户已有的系统（订单、工单、库存），同时不能变成"让模型访问任意网址"。
- **做法**：`service/tools/http_connector_tool.py`：每个连接器生成一个有名字的工具（如"查询订单状态"）。
  **URL、请求方式、认证头全部来自数据库里管理员预先配好的值，模型不能传**；每次请求前重新做 SSRF 校验（DNS 可能变）；
  请求头加密存储；响应体有大小上限，避免塞满上下文；带重试和熔断（`service/http_resilience.py`）。
- **追问**：客户接口很慢 / 返回很大 / 需要签名怎么办？→ 超时和响应上限已有；签名这类特殊认证需要现场做适配，这正是 FDE 的活。
- **后来发现的交付问题**：功能做了，但没人配得了——入口只在用户端，而且要求助手是操作人自己建的；企业智能体不在管理员名下，管理员打开只看到“无权限”，后台也没入口。补上后台「企业智能体 → 接口工具」（按“企业管理的智能体”授权、写审计、同名工具拒绝），用户端和后台共用一个组件。**功能存在 ≠ 用户用得上，交付前要按真实角色走一遍入口**。

### H. 数据隔离，以及怎么证明（信任）
- **做法**：所有"按 ID 取数据"走统一入口（`service/access_control.py` 的 `get_owned_*` 等），取不到就当不存在（404，不暴露"存在但无权限"）；
  知识库空间另有 owner / admin / editor / viewer 四种角色和审计日志。
- **证明**：`tests/test_routes_isolation.py` 用真实 JWT、真实数据库、真实路由验证跨用户访问一律 404 / 403。
- **最近的例子**：为管理员开放"维护所有技能"时，我补了真实路由测试，结果发现管理员访问已删除的技能会 500（应该是 404），
  修掉并加了断言。**说明"改权限必须配测试"**。

### I. 后台任务：多 Worker 怎么不重复干活（可靠性）
- **问题**：知识库入库、重建索引、组件定时刷新都是慢任务，不能卡住 API。
- **做法**：独立 Worker 进程（`service/background_worker.py`）；`claim_next_task` 用 `with_for_update(skip_locked=True)`，
  多个 Worker 不会抢到同一个任务；失败按退避时间写入 `next_run_at`，超过次数进入 failed，用户可手动重试；
  Worker 重启时把卡在 running 的任务重新排队（`requeue_stale_running_tasks`）。
- **追问**：为什么不用 Celery？→ 当前规模下多一个中间件的运维成本大于收益；任务表已经能表达状态、重试和审计。规模上来再换。

### J. 全链路联调发现的 bug（排障方法）
- **现象**：绑了工具的智谱模型助手，每次对话都 404。
- **过程**：单点测试都通过；跑全链路才复现；追到 `base_url` 被多拼了一次 `/chat/completions`。
- **结论**：只测单点不够，要跑全链路；这类问题在客户现场比在开发环境常见得多。

### K. 变更风险：所有用户共用一份技能配置，改错怎么办
- **问题**：技能改成"管理员维护、用户直接绑定同一份配置"后，管理员改错一次影响所有人。
- **做法**：① 每次编辑前自动存快照（去重，最多留 20 个），后台一键回滚，回滚前也会先存一份，"回滚错了"也能再回；
  ② 写配置改成"先写临时文件 → 校验 → `os.replace` 原子替换"（`service/skills_core/config_io.py`），校验失败线上配置原样保留；
  ③ 组合编辑只产生一个快照，快照失败不挡住编辑。见 `service/skills_core/versioning.py`。
- **FDE 视角**：客户环境里"改配置不能把线上改坏"，比"能改配置"更重要。

### L. 启动配置校验：把踩过的坑写成自动检查
- **做法**：生产模式启动时检查占位密钥（`change-me` 等）、弱管理员密码、Host / CORS 白名单未收紧、短信配置、加密密钥格式，
  **任何一项不合格直接启动失败**（`service/config_validation.py::assert_runtime_config`）。
- **FDE 视角**：交付给客户时，"带着示例密码上线"是最常见的事故；让系统自己拒绝，比靠文档提醒可靠。

下面六个是**测试、数据治理和交付**方面的故事（2026-10），面试官问"遇到过什么测试问题""脏数据怎么处理""上线交付出过什么问题"时讲。

### M. 只在空库上出现的 bug（测试环境和真实环境的差异）
- **问题**：CI 的后端测试连续几轮失败，本地怎么跑都是绿的。
- **判断**：先对比两边的起点——CI 每次是全新空库，本地开发库里早就有企业记录。猜测是"依赖现成数据"，用空库复现，果然：库里还没有企业时，
  用户管理、企业知识库、企业智能体三个列表直接报错。这在客户第一次部署时就是"后台打不开"。
- **做法**：① 读和写分开处理：列表在没有企业时返回空（`find_default_organization`），写操作才要求企业存在；
  ② 写 `scripts/test_fresh_db.py`：建临时库 → 迁移 → 跑两次初始化验证幂等 → 跑测试 → 删库，接进发布自检，推送前本地就能发现；
  ③ 根上解决：首次启动自动建企业（故事 P）。
- **结果**：空库上 24 条相关测试全过；顺带发现一处测试写法问题（空库上"管理员"测试账号其实不是管理员），也改了。
- **自己也踩了一次**：第一次跑完，`git status` 里两个提示词文件被删了——空库 id 从 1 开始，按 id 命名的文件和开发库共用目录，
  测试建的 1 号助手覆盖并删掉了开发库 1 号助手的文件。从 git 恢复，再把空库的自增起点抬到 9 亿。**测试工具本身也要考虑"会不会伤到旁边的数据"**。
- **还剩**：全量空库测试要十几分钟，日常只跑相关的一组，全量交给 CI。

### N. 发布后旧页面白屏，换个浏览器才能进（交付 / 缓存）
- **问题**：重新部署前端后，一个浏览器进不去页面，换浏览器就好。
- **判断**：不是账号问题，是浏览器里还开着**旧版本的页面**。旧页面按需加载旧的 JS 文件，新部署里已经没有了；nginx 把所有找不到的路径都回退成
  `index.html`，浏览器拿到一段 HTML 当 JS 执行，报 MIME 错误，白屏。另一个浏览器没有旧页面，所以正常。
- **做法**：① `/assets/` 找不到就 404，不回退；`index.html` 不缓存，带哈希的资源缓存一年；
  ② 前端捕获"加载旧文件失败"后自动刷新一次拿新版本，10 秒内不重复刷（防止死循环）；
  ③ 发现 `add_header` 写进 `location` 会让 server 级的安全头（CSP 等）整体失效，改用 `expires`。
- **验证**：`tests/test_nginx_delivery.py` 解析三份 nginx 配置；再起一个真实 nginx 容器，用 curl 逐个核对响应头和 404，安全头都还在。
- **FDE 视角**：客户那边"有人进不去"往往不是代码 bug，是部署和缓存。**能从现象推到部署层**，是这个岗位的基本功。

### O. 用着用着被登出（会话续期）
- **问题**：长时间不操作后进不去页面，要重新登录；更糟的是有人一直在用，60 分钟一到也被登出。
- **判断**：令牌固定 60 分钟、从不续期。但不能简单地"每次请求都续"——页面挂着不动，后台轮询（待办数、未读数）也在发请求，那就永远不过期了，
  等于没有登录时限。
- **做法**：滑动续期——剩余不到一半时才换新令牌；从登录算起最长 12 小时（`SESSION_MAX_HOURS`）必须重新登录；前端轮询带 `X-Background-Poll`，
  **不算"在用"**；只有浏览器 Cookie 登录续期，脚本用的 Bearer 令牌不续；令牌被吊销（改密码、停用）后的 401 不会被续期救回来。
- **验证**：`tests/test_session_renewal.py` 走真实 HTTP：快到期时续期，续期后带新 CSRF 的写请求能成功；轮询、Bearer、已吊销都不续。
- **FDE 视角**：安全（会话要过期）和体验（别打断正在干活的人）要同时满足，取舍要能讲清楚。

### P. 客户第一次部署，没有企业（交付自动化 + 幂等）
- **问题**：平台只服务一家企业，但空库第一次启动没有企业记录，要运维记得手动跑一个初始化脚本；漏了就是故事 M 里的"后台打不开"。
- **做法**：启动时检查，有用户但没有企业就自动建一条（名字可配），把已有用户加为成员（管理员为所有者），把无主的知识库挂上去。
  已经有企业就什么都不做；出错只记日志、不拦启动；`AUTO_CREATE_ENTERPRISE=0` 可关。
- **并发（评审指出后补的）**：一开始只调了 `GET_LOCK` 没看返回值——锁超时（返回 0）或出错（NULL）时照样往下建。改成没拿到锁就跳过；
  再加数据库兜底：建企业和写哨兵行（主键）在同一个事务里，哨兵行最先写，并发的第二个等第一个提交后撞主键、整体回滚。
  测试用 6 个线程同时初始化：绕过锁只靠哨兵行也只建出 1 家；反向验证——去掉哨兵行，6 个线程建出了 **6 家企业**，说明这个竞态是真的。
  **只靠应用层的锁不够，关键的唯一性要落到数据库约束上**。
- **验证**：在空库上测"创建"路径（`scripts/test_fresh_db.py` 里跑），在开发库上测"已存在不动"，还测了没有用户时跳过、开关关闭时不建。
- **FDE 视角**：**交付文档里每多一步手动操作，就多一个出错点**。能自动、能重复执行、执行两次结果一样，才适合放进启动流程。

### Q. 数据体检：脏数据从现象倒推不回来（数据治理）
- **问题**：文件导入时有逐行校验，但数据库里"已经在那儿"的问题没人系统查过——多出来的企业记录、没加入企业的用户、停用部门的助手还在发布、
  无主的知识库……页面上只表现为"某人看不到部门助手""某个知识库谁都看不到"，很难倒推回数据。
- **做法**：`scripts/data_health_check.py`：每项检查只读，给数量、几条样例、处理方法，分严重 / 注意 / 提示三级，有严重问题退出码为 1，接每日定时任务。
  **自动修复只做"补数据、不删数据、不需要人判断"的**（把用户加进企业、给知识库补上归属），修前先备份、修完写审计；
  保留哪家企业、停用部门的助手怎么办，只报告，由人决定。
- **结果**：第一次跑就查出一个**产品缺陷**：删除企业助手时只解绑、不删它专属的技能记录和配置文件，开发库里积了 50 个孤儿文件。修了删除逻辑，
  加了测试（反向验证过：去掉修复测试就失败）。已经存在的 50 个文件只报告，没有擅自删除——那是要和数据主人确认的事。
- **测试**：故意造脏数据（没进企业的用户、停用部门里还在发布的助手、无主空间、孤儿文件、残留测试账号），断言都能查出；
  `--fix` 只修该修的、写一条审计、修完再查就没有了；多条企业记录只报告不动。
- **FDE 视角**：客户现场的数据一定是脏的。**先查清楚、给出处理建议，能自动修的只修确定安全的，其余让人判断**，比"一键清理"可信得多。

### R. 数据保留期限（数据治理 / 合规）
- **问题**：每次对话都写运行轨迹，每个请求都写操作日志，通知和后台任务记录只增不减；上线一年后它们是库里最大的几张表，备份变慢，也没人说得清要留多久。
- **判断**：哪些能删、留多久，**是客户的决定**（有的行业有留存要求），不是工程师的决定。工程上要做的是：分清"过程记录"和"业务数据"，
  给出默认值，让删除可预览、可审计、不伤到在用的数据。
- **做法**：`service/data_retention.py` 按类配置天数（运行轨迹 180 天、操作日志 90 天、已读通知 180 天、已结束任务 90 天、已处理死信 180 天）；
  审计、问题中心、审批单、对话内容永远不删；运行中的、未读的、排队中的、待处理的不删；配 0 不清理、小于 7 天按 7 天算（防手误）；
  分批删、每批单独提交（不长时间锁表）；先只看数量、确认后 `--apply`，写审计；**自动清理默认关闭**，和客户确认后才打开。
- **测试**：测试数据放在 2001 年、把"现在"设成 2002 年，开发库里的真实数据不会被波及；断言到期的删了、不该删的都在、子表跟着删、
  重试任务只断开指向不被连带删除；反向验证过（让它删未读通知，测试就失败）。
- **还剩**：对话内容的保留期限（有的客户会要求）还没做，因为涉及用户资产，要先有产品层面的约定。

### S. "技能中心发布了，用户那边却是空的"（状态模型 + 界面误导）
- **现象**：管理员说技能都发布了，普通用户的技能中心一个都没有。
- **判断**：先查数据，不猜：用户端只显示"公开 **并且** 已发布"。库里 75 个技能全是"公开的草稿"——批量导入只设公开、不碰发布状态；
  后台卡片上"公开"标签很显眼，看起来像上架了。两套环境（本地和 Docker）一模一样，说明是流程问题，不是某个环境的数据坏了。
- **做法**：① 加"批量上架"（上架 = 公开 + 已发布，一步到位；部门助手专属技能跳过并说明原因；重复操作不重复写；写审计）；
  ② 卡片上直接写"已上架 / 未上架（私有、还没发布）"，不再让人从两个标签推断；③ 数据体检加一项"公开但没发布"。
  经确认后把 75 个全部上架（两套环境各写一条审计）。
- **顺带**：体检里孤儿配置文件越来越多，逐个模块跑定位到两个测试按名字删助手、没删配置文件，抽了公共清理函数。
- **同一批的另一个现象**：上架后部分技能显示“资源不存在、不可用”。资源文件都在，问题是导入时把 Windows 的绝对路径写进了配置，到 Linux 容器里路径不存在。读取时按 `skills_packages/` 段换算到本机，配置文件不动；在容器里实测 76 个导入技能从 13 个可用变成 76 个可用。一开始还顺手把写入改成相对路径，全量测试里有 10 条失败——有些代码直接读配置原文、按当前目录找路径。改动面越小越好：只在读取时换算，撤回写入的改动。
- **FDE 视角**：用户说"发布了"不等于系统里"已发布"。**一个结果由两个开关决定时，界面要直接说结果和原因**，否则每个客户现场都会问一遍。

## 4. FDE 场景题（12 道，用"先问 → 再判断 → 再方案 → 说边界"的结构答）

答场景题的通用模板：**① 先问清楚 2～3 个关键问题（不要直接给方案）→ ② 说你的判断依据 → ③ 给分阶段方案 → ④ 说风险和你不确定的地方。**

1. **客户的系统没有 API，只有数据库 / Excel。**
   先问：数据量多大？要实时还是每天更新？能否给只读账号？→ 三条路：让客户开一个只读接口（用连接器）；定期导出成文件进知识库；
   写一层很薄的适配服务。不要直接连客户生产库写操作，只读、限流、走白名单。

2. **客户要求"数据不能出内网"。**
   先问：不出内网是指数据、还是连模型调用也不能出？→ 私有化部署（Docker Compose）+ 模型 Key 由客户自己配；
   如果连模型也不能出，需要客户自己部署兼容 OpenAI 接口的模型，平台的模型地址是可配置的。**我没有实测过接本地模型，需要先在客户环境验证**（要主动说）。

3. **客户说"回答不准"。**
   先问：举 3 个具体的错误例子。→ 按链路排查：资料里有没有这个内容？检索有没有命中（调试台看命中片段和分数）？
   命中了但回答错（提示词 / 模型问题）？切块大小合不合适（可调 120～2000）？→ 把这几个例子存成评估集，改完回归。
   不要一上来就换模型。

4. **客户说"很慢"。**
   先问：哪一步慢——首字、整体、还是某类问题？→ 看运行步骤耗时（检索 / 工具 / 模型）；检索慢看向量库和重排序；工具慢看客户接口；
   模型慢看是不是流式（用户感知首字快）。有 `/metrics` 和运行轨迹可用。

5. **客户要"不同部门看不同资料"。**
   现状：知识库空间有 owner / admin / editor / viewer 角色，一个助手可绑多个空间。这能满足"部门级"；
   "公司 / 租户级"隔离**目前没做**，我评估过最小方案（成员表 + 一个用户只属于一家公司），需要时再做。先问清是部门还是独立公司。

6. **客户要单点登录（SSO）/ 对接企业微信、钉钉。**
   现状：只有账号密码 + 手机验证码，没有 SSO。诚实说没有；方案是先评估客户用的是 OIDC / SAML / 企业微信扫码，
   在登录层加一个适配，用户映射到现有用户表。这是交付时要跟客户确认的范围，不要现场承诺工期。

7. **上线后模型服务商挂了 / 限流了。**
   现状：请求有重试和熔断（`service/http_resilience.py`），熔断期间快速失败，不拖垮其它请求（熔断是每个进程各自的，不是全局的，多实例时要接 Redis，代码注释里写了）；用户自己的 Key，额度问题会给出明确提示。
   补充：客户可配多个模型；告警可推到飞书 / 钉钉（Webhook）。

8. **客户问"怎么保证我们的数据安全"。**
   分层答：传输（HTTPS）；存储（密码 bcrypt、模型 Key 加密存储）；隔离（按用户 / 空间，有测试）；访问外部（SSRF 防护，接口连接器不让模型传 URL）；
   审计（操作日志、知识库审计、运行轨迹）；运维（备份脚本、启动配置校验）。
   **最后补一句边界**：还没做第三方渗透测试，这是上线前应该做的。

9. **客户要求"某个操作要有审计"。**
   现有：操作日志中间件、`kb_audit_log`（知识库操作）、`AgentRun` / `AgentStep`（每次运行的每一步）。
   先问审计要留多久、谁能看、要不要导出，再决定是否加表。

10. **升级新版本出问题怎么回滚。**
    发布前：`scripts/release_check.py`（编译、全部测试、前端构建）+ `mysqldump` 备份 + 迁移评审；发布后：`/health` + 关键路径验证；
    回滚：回到上一个 git 版本重建镜像，数据库新增的表留着无害（迁移都是可重复执行的）。
    技能配置另有版本历史，能单独回滚。

11. **客户想自己写"技能"（工作流程）并带脚本。**
    现状的决定：**不开放用户自带脚本**，只有管理员导入并审核过的才能运行，且沙箱默认关闭。
    如果客户坚持要开放，前提是文件隔离、依赖管理、审计和配额都完善——这在 `docs/skill-extension.md` 里写了扩展路线，
    我会先跟客户讲清风险，而不是直接开放。

12. **客户预算有限，问"这个能跑多大规模"。**
    诚实答：目前是单机 Docker Compose，小规模上线；有压测脚本（`scripts/load_test.py`，`docs/load-testing.md`），
    但我不会报没测过的容量数字。方案是先按客户的并发和数据量在他们环境里压测，再决定要不要拆分数据库、多 Worker、换向量库部署方式。

## 5. 技术问答库

### 架构与工程
| 问题 | 回答要点 |
|---|---|
| 整体架构 | 路由层（鉴权、限流）→ 业务层（聊天、知识库、技能、配额）→ 数据层；运行时里有推理引擎、RAG、工具、技能四块。API 和 Worker 是两个进程 |
| 为什么同步和异步都有 | 分阶段迁移：聊天和大部分查询已是异步；技能管理的部分写入、RAG 检索仍是同步，用线程池桥接；边界写在 `docs/sync-async-boundary.md`。**别说成设计失误，说成有意识的迁移策略，并知道哪些还没迁** |
| 为什么向量库用服务模式 | API 和 Worker 是两个进程，内嵌模式不保证并发安全 |
| Redis 挂了怎么办 | 限流和缓存降级到内存，只保护当前进程；多进程下限流会变宽松，这是已知取舍 |
| 数据库迁移怎么做 | Alembic 迁移可重复执行；空库用初始化入口建表；发布前备份；已知的问题是"初始化和迁移尚未完全统一"，文档里写了 |
| 怎么测的 | 880 个测试：单元 + 真实路由级（真实数据库和 JWT）；改隔离、配额、限流、配置校验都有对应用例；CI 里跑 MySQL |

### Agent 与 RAG
| 问题 | 回答要点 |
|---|---|
| ReAct 循环怎么结束、怎么防死循环 | 没有工具调用就结束；`max_iterations`（默认 5）到了强制生成最终回答；支持用户取消；LangGraph 有递归上限 |
| 怎么防模型被诱导做坏事 | 工具是白名单；连接器 URL / 认证不接受模型传入；每次请求 SSRF 校验；技能脚本在沙箱里、默认关闭；迭代次数和用量有上限 |
| 检索为什么先校验权限再检索 | 先检索再过滤，会把别人的内容带进上下文、也浪费算力；权限放最前面最安全 |
| 切块大小怎么定 | 可调 120～2000；太小上下文碎，太大噪声多；要按客户资料类型用评估集调 |
| 怎么评估 RAG 效果 | 调试台存样例、评估集回归、健康报告的命中 / 拒答 / 引用率 |
| 为什么让用户自带 Key（BYOK） | 平台不垫模型成本，用量和成本归属清楚；代价是用户要自己配置，所以做了"一次连接多项能力" |

### 安全
| 问题 | 回答要点 |
|---|---|
| SSRF 怎么防 | 抓取和连接器每次请求前都校验目标地址（DNS 可能变，不能只信配置时那一次） |
| 密码和 Key 怎么存 | 密码 bcrypt；模型 Key 和连接器请求头加密存储（Fernet，密钥在环境变量）；启动时校验密钥格式 |
| 验证码怎么防暴力破解 | 单码错 5 次作废 + 按手机号原子频率限制 + 发送频率 + 全站总量（故事 C） |
| JWT 怎么处理 | 有过期时间；账号被禁用后请求会被拒（走用户状态校验）；密钥启动时校验 |
| 上传文件的风险 | 大小 / 数量 / 类型限制；zip 防路径穿越和解压炸弹（条目数、解压后大小上限）；导入的配置不能指向任意目录 |

### 部署与运维
| 问题 | 回答要点 |
|---|---|
| 怎么部署 | Docker Compose 拉起 db / redis / chroma / api / worker；宿主机 nginx + certbot 做 HTTPS；api 只绑本机回环 |
| 怎么发现线上问题 | `/health` 探活、`/metrics` + 告警规则、操作日志、后台"系统诊断"页、告警 Webhook |
| 备份 | `scripts/backup.py`（可 cron，自动清旧备份）；发布前 `mysqldump` |
| 你的 nginx 做了什么 | 静态托管、`/api` 反代（聊天流式单独调超时）、安全响应头、上传大小限制；HTTPS 在这一层终结 |
| 环境变量太多怎么管 | `.env.production.example` 是唯一清单；启动配置校验拒绝占位值；文档里每项都有说明 |

### 前端
| 问题 | 回答要点 |
|---|---|
| 流式怎么做 | SSE，前端 `sendStream` 逐事件渲染（思考 / 工具 / 检索 / 回答） |
| 主题和深色模式 | 设计令牌集中管理，深色靠翻转色阶变量 |
| 怎么验证 UI | 类型检查（vue-tsc）+ 用 Playwright 加路由 mock 在真实浏览器里点过关键页面 |

## 6. 行为题（用 STAR：情境 → 任务 → 行动 → 结果）

| 问题 | 用哪个素材 |
|---|---|
| 讲一个你解决过的最难的问题 | 故事 J（全链路 404）或故事 B（nginx 后面限流），重点讲"怎么一步步缩小范围" |
| 讲一次你判断错了 / 有遗漏的经历 | 故事 C：一开始以为短信限制够了，逐项检查才发现 4 个缺口；或故事 K：共享配置后才意识到改错的影响面 |
| 时间紧、需求多，怎么排优先级 | 先做"会造成钱或数据出问题"的（额度、隔离、防刷），再做体验；每次改动都带测试，避免回头返工 |
| 怎么和不懂技术的人沟通 | 用"前台 / 办事员 / 大脑 / 资料室"这套比喻（见 `code-walkthrough.md`）；先讲对客户的影响，再讲原因 |
| 你怎么学新东西 | 边做边读文档；每个新模块开头写中文说明；不懂的先做最小可运行版本再迭代（沙箱就是这样：先设计边界、默认关闭、再写验收脚本） |
| 遇到不会的问题怎么办 | 先缩小范围、用日志和测试验证假设，再查资料；实在不行就明确告诉对方"这个我需要验证，不乱承诺" |
| 你对 AI 辅助编码怎么看 | 如实说使用；关键是**每个设计取舍我能讲清、每处改动有测试、上线前自己验证**；把它当作提速工具，责任在我 |

## 7. 五分钟演示脚本（提前彩排两遍）

演示前：账号已登录、模型 Key 有余额、知识库里有一份**你熟悉内容**的文档、页面缩放合适。**准备一个备用录屏，网络出问题时用。**

| 时间 | 做什么 | 边做边说的话 |
|---|---|---|
| 0:00 | 打开工作台 | "这是用户登录后的工作台，能看到本月用量，这是配额功能" |
| 0:30 | 进知识库中心，展示已上传的文档和状态 | "文档上传后由后台 Worker 入库，慢任务不卡页面" |
| 1:30 | 进助手，提一个**文档里有答案**的问题 | 指出流式输出、"参考来源"；"每条回答可以对回资料" |
| 2:30 | 提一个**文档里没有**的问题 | "这里它会拒答，而不是编一个——企业场景里瞎编比不知道更危险" |
| 3:15 | 打开运行检查 / 调试台，看一次运行的每一步 | "出问题时我能看到是检索、工具还是模型的问题" |
| 4:00 | 切到管理员后台：技能中心 → 一个技能的历史版本 | "所有人共用一份配置，所以每次编辑前自动存快照，一键回滚" |
| 4:40 | 收尾 | "还有很多没演示的，比如接口连接器和沙箱——您想深入哪块？" |

**演示翻车预案**：Key 余额不足 → 用备用录屏；线上打不开 → 本地跑一份（提前确认能启动）；被问到没做的功能 → 直接说"目前没做，我的想法是……"。

## 8. 简历写法

**原则**：写你能讲清的、有事实依据的。数字用真实可核对的（测试数、模块数），不要写没测过的性能数字。

项目名（示例）：**多用户 AI 智能体平台（个人项目，已部署上线）**
技术栈：Python / FastAPI / SQLAlchemy / MySQL / Redis / ChromaDB / LangGraph / Vue3 / TypeScript / Docker Compose / Nginx

可选要点（挑 4～5 条，按岗位相关性排序）：
- 设计并实现多用户智能体平台，支持自带模型 Key、知识库检索（带来源引用与低置信度拒答）、工具调用和流式对话；使用 Docker Compose 部署到阿里云 ECS。
- 实现企业接口连接器：连接器的地址与认证由管理员配置、模型不可传入，每次请求前进行 SSRF 校验，并带重试、熔断和响应大小限制。
- 设计"先检查额度再调用模型"的配额机制与多级限流（登录 / 注册 / 短信 / 聊天），并补齐短信验证码防刷（全站封顶、原子校验计数）。
- 建立数据隔离与真实路由级测试（真实 JWT + 数据库），项目共 880 个测试用例并接入 CI；编写发布检查、备份脚本与生产启动配置校验。
- 设计技能脚本沙箱（独立容器、无外网、默认关闭、管理员审核）与技能版本回滚；排查并解决 nginx 反代下客户端真实 IP 识别等部署问题。

**别写**：高并发 / 高可用 / 企业级 / 支持百万用户 / 性能提升 X 倍——没有数据支撑就不写。

## 9. 别这样说

- 不要说"我做了企业级 / 高并发 / 高可用"。项目是单机 Docker Compose，小规模上线。
- 不要说"完全防住了 XXX"。说"做了哪几层防护，还有哪些边界"。
- 不要说线上出过事故（限流、短信）——除非真发生过。
- 不要背功能列表。面试官记不住 30 个功能，记得住 1～2 个讲得透的故事。
- 没做的就说没做（被问“能不能直接给大企业用”时按这个清单答，不要包装成成熟 SaaS）：
  - **部署形态**：单机 Docker Compose、默认只服务一家企业；没有多实例高可用、数据库主从 / 故障切换，也没做过 RTO / RPO 演练；
  - **身份**：没有 SSO（OIDC / SAML）、没有 LDAP / SCIM 组织同步、管理员没有 MFA；
  - **安全验证**：没做过第三方渗透测试；脚本沙箱默认关闭，容器隔离没在实机验收；
  - **容量**：有压测脚本，但没有生产规模的容量验证；
  - **多租户**：没有多公司隔离。
  这些不影响演示“一个企业从部署到用起来”的完整链路；被追问时说清楚“做到哪一步、下一步怎么做”。
- 不要现场翻目录、滚动读代码：事先把 5 个文件开成标签页（`react_engine.py`、`space_search.py`、`http_connector_tool.py`、`access_control.py`、`config_validation.py`）。
- 被问"是你写的吗"：如实说用了 AI 辅助，然后立刻讲一个设计取舍或一个你排过的 bug。**能讲清楚就是最好的回答。**

## 10. 反问面试官（选三个）

- 团队的客户主要是什么行业、什么规模？部署形态是私有化还是云上？
- 新人第一个月会跟什么类型的项目？多久会独立对接客户？
- 现场遇到需要产品改动的需求，反馈到产品团队的流程是什么样的？
- 你们交付里最常见的坑是什么？（你可以接一句"我上线时遇到过环境差异和反向代理的问题"）
- 储备岗转正的标准是什么？
