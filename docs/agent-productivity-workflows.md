# Agent 工作成果：本地使用与验收

部门工作台的"让 AI 帮我整理工作"把员工粘贴的材料整理成结构化结果，员工核对、修改后保存为 Java 业务系统里的**草稿**。正式提交、审批仍在对应业务模块办理，Agent 不会自动提交或审批。

| 工作类型 | 可用部门 | 输出 | 写入的业务草稿 |
|---|---|---|---|
| 沟通记录 → CRM 跟进与待办 | 业务类型为"销售"的部门 | 跟进内容、原文依据、后续待办、疑点 | CRM 客户跟进记录 |
| 费用材料 → 报销草稿 | 所有部门 | 费用分类、金额、发票号、疑点 | 报销单 |
| 请假描述 → OA 请假草稿 | 所有部门 | 假期类型、起止日期、原因 | 请假单 |
| 采购需求 → 采购申请草稿 | 业务类型为"采购"的部门 | 产品 SKU、数量 | 采购申请（金额由产品目录计算） |

部门的业务类型在"管理后台 → 组织架构 → 部门管理 → 重命名"中设置。

## 业务系统核对

整理结果出来后，服务端会拿它去查真实业务数据（只读），结论显示在核对页的"业务系统核对"区块，分三级：**会被拒绝**（按业务规则保存/提交会失败）、**需确认**、**参考**。员工修改内容后会提示结论可能过期，可点"重新核对业务数据"（`POST /enterprise/automation/{id}/checks`）。

| 工作流 | 核对内容 |
|---|---|
| 采购 | SKU 是否在产品目录（不在则"会被拒绝"）；库存、安全库存、单价与本次金额；库存已充足时提醒确认是否必要；预计金额与部门剩余采购预算；是否已在你未完成的采购申请里（防重复采购） |
| 报销 | 发票号是否已被其他未驳回报销单使用（"会被拒绝"）；缺发票的费用条数；报销合计与部门剩余报销预算 |
| 请假 | 对应年度假期余额是否足够；与已有未驳回请假单是否时间重叠 |
| CRM | 客户上次跟进日期与距今天数、在谈商机（阶段与金额，提醒在 CRM 模块更新）、没有截止日期的待办 |

**重复发票由 Java 业务层强制**：同一张发票不能出现在两张未驳回的报销单里（同一报销单内也不能重复），无论从报销模块、Agent 工具还是 AI 材料整理录入；被驳回的报销单不占用发票。核对用的只读接口为 `GET /finance/invoices/usage?numbers=`（权限范围 `finance.read`）。

核对失败（业务服务不可用）不影响整理结果本身，只显示一条"未能完成核对"的提示；最终仍以保存时业务系统的校验为准。

## 工作流注册机制（新增一类工作）

每类工作是 `service/workflows/` 下的一份声明（`WorkflowDefinition`），状态机（整理中 / 待核对 / 保存中 / 保存待重试 / 已保存）、幂等键、权限、额度、统计、重试规则全部由 `service/automation_work_service.py` 统一提供。新增"合同审查""招聘简历整理"等工作流时只需要：

1. 新建 `service/workflows/<名称>.py`，声明：
   - `departments`：允许使用的部门业务类型（`None` 为所有部门），`preferred_for`：哪些部门默认选中；
   - `schema`：模型输出的 Pydantic 模型（`StrictModel`，额外字段一律拒绝，必须含 `warnings`）；
   - `instructions`：只属于这类工作的整理要求（通用的防注入、原文依据规则自动拼在前面）；
   - `evidence`：哪些字段必须逐字出现在原文中；`check`：额外业务规则（`for_save=True` 时更严格）；
   - `precheck`：调用模型前的真实业务数据预查询（如 CRM 校验客户属于本部门）；
   - `form`：人工核对表单描述（text / textarea / date / select / integer / money / evidence / list / note / sum），前端 `WorkflowForm.vue` 按描述渲染并做保存前校验；
   - `write`：核对后内容 → Java 草稿接口（路径、权限范围、操作名、请求体）；
   - `followups`：可选，成果中的后续待办字段。
2. 在 `service/workflows/__init__.py` 的 `_BUILTIN` 中登记。

前端不需要改动：工作类型、表单、校验文案都来自 `GET /enterprise/automation/workflows?team_id=`。`tests/test_workflow_registry.py` 演示了运行时注册一个"合同审查"工作流并走完整理→核对→保存草稿全流程；同一文件的完整性测试会检查每个注册工作流的表单字段都存在于 schema 中。成果统计按工作流分别给出（`stats.by_kind`）。

## 部门专业 Agent 自动配置

每个部门按业务类型自动拥有一个主 Agent，管理员不需要再手工创建：

| 部门业务类型 | 自动配置的 Agent | 专业技能（工具） |
|---|---|---|
| 人事 | OA 人事助手 | 请假余额、草稿、提交、审批、进度 |
| 采购 | 采购与库存助手 | 库存、部门预算、采购申请、审批 |
| 销售 | CRM 客户与商机助手 | 客户、跟进、商机 |
| 财务 | 财务报销助手 | 报销预算、报销单、审批 |
| IT | IT 服务助手 | 目前为请假与报销；IT 工单/账号/设备模块尚未上线 |
| 未设置 | 部门办公助手 | 请假与报销 |

- **建部门、修改业务类型、重新启用部门**时自动生成或恢复草稿 Agent，并绑定该 Agent 独立的专业技能；修改业务类型时，旧的已发布 Agent 会退役。
- **停用部门**时，该部门已发布的 Agent 同步退役。
- **发布唯一性按部门**：同一部门同时只能有一个已发布的部门 Agent；不同部门（如销售一部、二部）可各自发布。发布前检查模型是否为可用聊天模型、部门是否启用、Agent 业务方向是否与部门一致。
- 管理后台"组织架构 → 部门管理"选中部门即可看到 **部门专业 Agent** 状态：已发布 / 待发布 / 需要修复（附缺失原因）/ 部门已停用，并提供 **一键修复** 与 **发布给部门员工**。
- 员工在部门工作台能看到部门助手；未发布时显示原因，未连接模型时提示去"设置 → 模型连接"。
- 接口：`GET /admin/org/teams/{id}/agent-status`、`POST .../agent-repair`、`POST .../agent-publish`。迁移 `20261002_0001` 会按存量部门 Agent 回填部门业务类型，并把发布唯一键改为按部门。

## 启动

沿用项目现有 `.env`。先启动 MySQL，再在项目根目录运行：

```powershell
npm run db:migrate        # Alembic 升级到 20261001_0002（automation_work 表）
npm run backend:dev
npm run backend:worker
npm run frontend:dev
```

保存业务草稿需要 Java 服务：进入 `enterprise-business-hub` 运行 `mvn spring-boot:run`（默认端口 8090）。`ENTERPRISE_DB_*` 指向企业业务库，`ENTERPRISE_HUB_HMAC_SECRET` 必须与 Python 一致；Java 不读取根目录的 `.env`，详见 [企业业务服务说明](enterprise-business-hub-plan.md)。

打开 http://localhost:5173/department ，在"设置 → 模型连接"启用一个聊天模型后即可使用。

## 手工验收

1. **CRM**（销售部门）：选择客户，粘贴 `2026年10月1日与客户沟通，对方希望先试用。约定2026年10月8日发送方案；预算尚未确定。` 检查跟进内容、原文依据、待办日期和疑点，可修改或删除待办；勾选核对后保存，在下方 CRM 模块查看草稿，在成果面板勾选完成待办。
2. **报销**：粘贴 `10月1日出差高铁票260元，发票号G001；出租车48元，暂无发票。` 检查分类、金额、发票号和合计后保存，在报销模块查看草稿。
3. **请假**：粘贴 `我要申请年假，2026年10月12日至2026年10月14日，原因是家庭事务。` 若原文日期不完整，模型留空并提示，补全后才能保存；在"我的请假"查看草稿。
4. **采购**（采购部门）：粘贴含真实 SKU 的需求。填写不存在的 SKU 时，业务系统会拒绝并显示原因（如"未知产品: XXX"），成果退回可修改状态，改正后即可保存。
5. 刷新页面，历史成果和待办状态仍在；其他账号看不到你的成果；退出部门后不能继续访问或保存。
6. Java 服务不可用时，保存结果显示"保存待重试"，内容锁定；恢复后按原内容重试，不会产生重复草稿。

## 保存与重试规则

- 每份成果只有一个固定的 Java 幂等键 `automation-{成果ID}`，首次保存及所有重试都用它。
- **业务系统明确拒绝**（HTTP 400/403/404/422，例如未知产品、客户不存在、字段不合法）：Java 的业务异常会让幂等占位记录随事务一起回滚，这个键下没有任何写入，因此成果退回"待核对"，用户可修改内容后用同一个键重新保存。该不变式由 Java 测试 `rejectedDraft_rollsBackIdempotencyKey_soCorrectedBodyCanReuseIt` 守护。
- **结果不确定**（超时、409 正在处理、5xx）：成果进入"保存待重试"，内容锁定，只允许按原内容重试；若 Java 其实已经写入，重试会拿到第一次的结果，不会重复创建。
- 业务原因（"预算不足"、"未知产品"等）由 Java 的 `ApiExceptionHandler` 返回、Python 原样展示；其它异常只显示通用说明，不暴露内部信息。

## 实现与边界

- 原文、模型输出、核对后内容、业务结果、耗时及 Token 用量保存在 MySQL `automation_work` 表；月度额度统计包含这些调用。
- 模型输出必须通过严格 schema 和原文依据校验：每条 evidence 必须逐字出现在原文中，金额、日期、数量有格式校验，同批发票号和 SKU 不能重复，模型不能附加价格或提交指令。
- 支持粘贴及 UTF-8 TXT/Markdown/CSV 导入，最多 15,000 字；费用仅支持人民币。不包含图片/PDF OCR、凭证过账或自动付款。
- 材料密级为"受限"时禁止调用模型；"机密"只能用受信任模型。
- 待办属于当前用户的工作成果，不会自动分派、发邮件或推送提醒。
- 生成超时 90 秒；进程中断留下的"整理中"记录超过 3 分钟后会被标记为失败，可带回原文重新整理。
- 统计展示处理、保存、失败、修改数量和实际整理耗时；没有把模型耗时包装成"节省的人工时间"。
