# Agent 工作成果：本地使用与验收

部门工作台的"让 AI 帮我整理工作"把员工粘贴的材料整理成结构化结果，员工核对、修改后保存为 Java 业务系统里的**草稿**。正式提交、审批仍在对应业务模块办理，Agent 不会自动提交或审批。

| 工作类型 | 可用部门 | 输出 | 写入的业务草稿 |
|---|---|---|---|
| 沟通记录 → CRM 跟进与待办 | 业务类型为"销售"的部门 | 跟进内容、原文依据、后续待办、疑点 | CRM 客户跟进记录 |
| 费用材料 → 报销草稿 | 所有部门 | 费用分类、金额、发票号、疑点 | 报销单 |
| 请假描述 → OA 请假草稿 | 所有部门 | 假期类型、起止日期、原因 | 请假单 |
| 采购需求 → 采购申请草稿 | 业务类型为"采购"的部门 | 产品 SKU、数量 | 采购申请（金额由产品目录计算） |

部门的业务类型在"管理后台 → 组织架构 → 部门管理 → 重命名"中设置。

## 业务系统核对

整理结果出来后，服务端会拿它去查真实业务数据（只读），结论显示在核对页的"业务系统核对"区块，分三级：**会被拒绝**（按业务规则保存/提交会失败）、**需确认**、**参考**。员工修改内容后会提示结论可能过期，可点"重新核对业务数据"（`POST /enterprise/automation/{id}/checks`）。

| 工作流 | 核对内容 |
|---|---|
| 采购 | SKU 是否在产品目录（不在则"会被拒绝"）；库存、安全库存、单价与本次金额；库存已充足时提醒确认是否必要；预计金额与部门剩余采购预算；是否已在你未完成的采购申请里（防重复采购） |
| 报销 | 发票号是否已被其他未驳回报销单使用（"会被拒绝"）；缺发票的费用条数；报销合计与部门剩余报销预算 |
| 请假 | 对应年度假期余额是否足够；与已有未驳回请假单是否时间重叠 |
| CRM | 客户上次跟进日期与距今天数、在谈商机（阶段与金额，提醒在 CRM 模块更新）、没有截止日期的待办 |

**重复发票由 Java 业务层强制**：同一张发票不能出现在两张未驳回的报销单里（同一报销单内也不能重复），无论从报销模块、Agent 工具还是 AI 材料整理录入；被驳回的报销单不占用发票。核对用的只读接口为 `GET /finance/invoices/usage?numbers=`（权限范围 `finance.read`）。

核对失败（业务服务不可用）不影响整理结果本身，只显示一条"未能完成核对"的提示；最终仍以保存时业务系统的校验为准。

## 中央 Agent 转交

员工在「部门工作台」页底部看到"不确定该找哪个部门？"入口，进入企业中央助手（`/agents/{id}/chat`；中央/部门助手由管理员创建，不在员工自己的助手列表里，聊天页按 id 单独取并校验使用权限）。在中央助手里发起**新会话**时：

1. 用各部门模板里的 `routing_keywords` 匹配问题，命中词越多的部门越靠前，相同时按模板声明顺序。
2. 只在**你有权使用的已发布部门助手**里找（你所属部门的那个）。命中最强且可用的部门助手接手这次会话；会话从此绑定该助手。
3. 同一个问题涉及多个部门时，其余可用的部门作为"备选"给出，点"改问「X 助手」"进入该助手的新会话；命中但你没有可用助手的部门会明确提示，而不是悄悄丢掉；一个都没有可用时由中央助手自己回答并说明原因。
4. 路由结果：流式对话开头有一个 `route` SSE 事件，同步接口的返回里带 `routing` 字段，聊天页据此显示转交说明。
5. 每次中央助手的决定（已转交 / 未命中 / 命中但无可用助手）都写入 `agent_handoff`（用户、中央助手、目标助手、原因、命中词、备选、输入摘要前 500 字），管理员通过 `GET /admin/org/handoffs` 查询。
6. 已有会话继续用创建时绑定的助手，不重新路由；高风险写操作（提交、审批、拒绝）本来就要在会话里逐项确认后才会执行。

**目前不做**：一个问题拆成多个部门子任务并行执行、再汇总回复。那需要一个能同时驱动多个部门助手的运行时，现在每个会话只绑定一个助手；多部门问题通过"备选"让用户明确切换。关键词路由也不理解语义，措辞不含关键词的问题会由中央助手自己回答。

## 效果指标

管理后台"AI 工作成果"页（`GET /admin/automation-metrics?days=&team_id=`）按工作流给出可从系统数据直接算出的指标：

| 指标 | 含义 |
|---|---|
| 保存率 | 处理的材料中最终保存为业务草稿的比例 |
| 一次通过率 | 已保存成果里"员工没改过内容且一次保存成功"的比例（试点目标 ≥ 80%） |
| 平均修改比例 | 已保存成果里员工改动的字段占比（值变化、新增、删除都算一处；原文依据和疑点不算） |
| 重试率 | 保存时至少重试过一次的比例 |
| 整理耗时 / 办结耗时 | 模型处理时间 / 从提交材料到保存业务草稿（含员工核对时间）的中位数（目标：CRM ≤ 2 分钟，报销 ≤ 3 分钟） |
| 业务系统核对拦截 | 核对出"会被拒绝"问题的成果数 |
| 业务草稿重复创建 | 已保存成果中指向同一业务单号的重复数（试点目标 0，由幂等键保证） |
| Token / 份、成本 | 每份已保存成果消耗的 Token；配置 `AUTOMATION_TOKEN_PRICE_PER_1K` 后折算人民币，未配置则不估算金额 |

**估算节省时间** = (手工基准 − 办结中位数) × 已保存份数，不会为负。手工基准是管理员在该页为每类工作设定的"手工办理一次要多久"（默认 CRM 12 / 报销 15 / 请假 6 / 采购 15 分钟），是估算值而不是实测，页面上明确标注。采购需求"录入时间降低 50%"这类目标需要先用真实试点测出手工基准再对比。样本太少时比例仅供参考。

## 待办中心与主动提醒

侧栏"我的待办"（`/todos`）汇总三类事项，角标显示逾期和今天到期的数量；铃铛显示站内通知。

- **业务提醒**：后台 Worker 定时运行提醒规则，生成待办并发一次站内通知；条件不再成立（已审批、已跟进、已补发票）时自动关闭，条件再次成立时重新打开；用户主动"忽略"的不会被重新打开。
- **AI 成果后续事项**：CRM 跟进保存后，其中的后续待办自动进入待办中心，两边勾选完成状态同步。
- **我记的**：手工添加，可设截止日期（只填日期时为北京时间当天 18:00）和优先级。

| 规则 | 提醒谁 | 条件 | 默认间隔 |
|---|---|---|---|
| 审批等待超时 | 部门负责人（部门没有负责人时为企业所有者/管理员） | 请假/采购/报销提交超过 `REMIND_APPROVAL_WAIT_HOURS`（默认 24）小时未审批；等待超过 3 倍时限或请假 2 天内开始时为高优先级；不提醒审批自己提交的单据 | 30 分钟 |
| 客户长期未跟进 | 客户负责人（已不在部门时给部门负责人） | 超过 `REMIND_CUSTOMER_STALE_DAYS`（默认 14）天没有跟进 | 6 小时 |
| 报销缺发票 | 申请人 | 草稿或待审批报销单中有费用没有发票号 | 6 小时 |
| 待办到期 | 待办负责人 | AI 成果待办或手工待办 24 小时内到期或已逾期（只通知一次） | 15 分钟 |
| 每周工作摘要 | 部门负责人 | 每周一份：近 7 天 AI 整理与保存数量、超时待审批数量 | 每天检查，每周一次 |

- 调用业务系统时以"本来就有权看到这些数据的人"的身份签名（部门负责人看本部门待审批、员工看自己的报销单），权限标志如实计算，不提权。
- 每条规则有独立租约，多个 Worker 同时运行也只执行一次；单条规则失败不影响其它规则，按间隔自动重试，连续失败 3 次通知企业所有者/管理员。管理后台"系统诊断"可查看每条规则的上次结果、下次运行时间并"立即运行"。
- 通知设置（待办页底部）：按类别静音、免打扰时段（北京时间，只影响外部推送）、是否同时推送到"设置 → 通知通道"里配置的群机器人。
- 环境变量：`REMINDERS_ENABLED=0` 关闭提醒；`REMINDER_POLL_SECONDS`（默认 60）控制 Worker 检查频率。
- 接口：`GET/POST /work-items`、`PATCH /work-items/{id}`、`GET /work-items/counts`、`GET /notifications`、`POST /notifications/read`、`GET/PUT /notification-preferences`、`GET /admin/reminders`、`POST /admin/reminders/{rule}/run`。

## 工作流注册机制（新增一类工作）

每类工作是 `service/workflows/` 下的一份声明（`WorkflowDefinition`），状态机（整理中 / 待核对 / 保存中 / 保存待重试 / 已保存）、幂等键、权限、额度、统计、重试规则全部由 `service/automation_work_service.py` 统一提供。新增"合同审查""招聘简历整理"等工作流时只需要：

1. 新建 `service/workflows/<名称>.py`，声明：
   - `departments`：允许使用的部门业务类型（`None` 为所有部门），`preferred_for`：哪些部门默认选中；
   - `schema`：模型输出的 Pydantic 模型（`StrictModel`，额外字段一律拒绝，必须含 `warnings`）；
   - `instructions`：只属于这类工作的整理要求（通用的防注入、原文依据规则自动拼在前面）；
   - `evidence`：哪些字段必须逐字出现在原文中；`check`：额外业务规则（`for_save=True` 时更严格）；
   - `precheck`：调用模型前的真实业务数据预查询（如 CRM 校验客户属于本部门）；
   - `form`：人工核对表单描述（text / textarea / date / select / integer / money / evidence / list / note / sum），前端 `WorkflowForm.vue` 按描述渲染并做保存前校验；
   - `write`：核对后内容 → Java 草稿接口（路径、权限范围、操作名、请求体）；
   - `followups`：可选，成果中的后续待办字段。
2. 在 `service/workflows/__init__.py` 的 `_BUILTIN` 中登记。

前端不需要改动：工作类型、表单、校验文案都来自 `GET /enterprise/automation/workflows?team_id=`。`tests/test_workflow_registry.py` 演示了运行时注册一个"合同审查"工作流并走完整理→核对→保存草稿全流程；同一文件的完整性测试会检查每个注册工作流的表单字段都存在于 schema 中。成果统计按工作流分别给出（`stats.by_kind`）。

## 权限边界（后端强制，前端隐藏只是体验）

所有部门业务接口（请假、采购、CRM、报销、AI 工作成果）和 Agent 工具在 `service/department_access.py` 统一校验，直接请求接口也绕不过：

1. **身份四层有效**：企业有效、本人企业成员身份有效、部门有效、本人部门成员身份有效。部门成员/部门负责人判断统一要求企业成员身份有效——成员被停用或移出企业后，残留的部门成员记录不再给出任何部门权限（部门助手、部门知识库、审批权限都失效）。
2. **业务模块与部门业务类型一致**：采购模块只给"采购"部门，CRM 只给"销售"部门，请假和报销是所有部门通用的办公事务。部门没设业务类型时，采购和 CRM 同样被拒绝。
3. **部门助手的部门上下文**：Agent 工具用部门助手所在的部门，但只有调用者本人是该部门有效成员（或企业管理员）才采用——助手的创建者不是部门成员时，不能借助手的部门身份往部门里写业务数据；兜底的"在职第一个部门"同样要求企业成员身份有效。

校验规则的测试在 `tests/test_department_access.py`（直接请求接口、停用成员/部门/企业、工具侧、部门助手上下文）。

## 财务自动记账（报销批准 → 凭证草稿 → 人工核对 → 入账）

流程：员工提交报销 → 部门负责人批准 → **同一事务里**自动生成记账凭证草稿 → 财务人员核对科目与风险 → 确认入账 → 月度汇总。系统只"建议"，不替人决定入账。

- **科目建议**：借方每条报销明细一行，贷方汇总到"其他应付款-员工报销款（2241.01）"。科目由规则表 `subject_rule` 给出（类别默认 + 说明关键词，如"客户宴请"→业务招待费），销售部门走销售费用（6601），其他部门走管理费用（6602）。每行带**依据**和**置信度**（规则确定 / 推断 / 低置信 / 人工）；判断不了的明确标低置信、暂记"其他"。
- **风险检查**（`VoucherRiskChecker`，全是确定性规则，每次生成/改动/重新检查/确认都重算）：借贷不平衡、科目失效、重复发票（阻断）；无发票、大额（≥5000）、14 天内同人同类别同金额的疑似重复、低置信科目、跨期入账、预算已用完（需核对）；业务招待费、推断科目（提示）。**阻断项不处理不能入账；需核对项必须由财务明确勾选"已核对风险项"。**
- **权限**：只有财务类型部门（`department_code=finance`）的有效成员或企业管理员能用，可见范围限定在同一企业；业务部门（含销售、人事）直接请求也被拒绝。FastAPI 先判断再签 `finance.voucher.read/write`，范围 `scopeTeamIds` 写在已签名的路径里，Java 再限定一次（范围外一律 404）。**申请人不能确认自己报销单的凭证**（制单与复核分离）。
- **可追溯**：改科目必须写原因（记录改自哪个科目），每次生成/改科目/改日期/入账/作废都写审计事件；凭证号按期间连续编号（`记-YYYYMM-NNNN`，期间序号行加锁，并发确认不会重号）。
- **补生成**：上线前已批准、或自动生成失败的报销单出现在"待生成"列表，一键补生成。
- **Agent 工具**：`list_pending_vouchers`、`get_voucher_detail`、`generate_voucher_draft`、`get_voucher_monthly_summary`。**刻意没有确认入账/作废/改科目的工具**，即使模型被诱导也没有能入账的工具可调。
- **提醒**：规则 `pending_voucher` 提醒财务部门成员"有 N 张凭证待核对（其中 M 张有风险）/有已批准报销单没有凭证"，核对完自动关闭。
- **同时修复**：同一报销单被两个审批人并发批准会重复扣预算（现在审批加行锁，`concurrentApprovalDeductsBudgetOnce…` 测试在去掉锁时失败）。

限制（有意不做）：不做红字冲销/反结账（已入账凭证不可改，更正需另做凭证）；不对接外部总账/ERP；科目表是小企业常用费用类科目，不是完整会计科目表；不做期间关账。

测试：Java `VoucherControllerIntegrationTest`（16 项，真实 MySQL + 签名上下文）、`tests/test_finance_vouchers.py`（权限层）、`tests/test_finance_voucher_tools.py`、`tests/test_work_center.py`（提醒）、`scripts/e2e_finance_vouchers.py`（真实端到端 43 项，`--keep` 保留数据供浏览器验证，`--purge` 清理）。

## IT 服务台（工单、SLA、设备台账）

流程：员工提交工单 →（账号/权限/设备申请先由申请人所在部门负责人批准）→ IT 接单 → 处理 / 等待用户补充 → 解决 → 申请人确认关闭（没解决可重新打开）。

- **提交前先自助**：输入问题描述时实时给出自助排查方案（关键词匹配的知识条目，如打印机、VPN、密码、邮箱、网络）和规则对类型/优先级的判断（带依据）；能自己解决就不用提交。规则只做建议，不覆盖你填的类型，IT 人员能看到“系统建议 vs 当前”的差异。
- **审批分流**：账号、权限、设备申请涉及资源或成本，必须先由申请人所在部门的负责人（或企业管理员）批准，不能批准自己的；批准前不进 IT 队列，IT 也无法操作。忘记密码、账号被锁属于故障，不走审批。IT 把故障改成需审批的类型来绕过流程会被拒绝。
- **SLA**：按优先级计时（紧急 4h / 高 8h / 普通 24h / 低 72h），队列按截止时间排序，状态分正常/即将超时/已超时/暂停/按时。“等待用户”期间暂停，用户回复后截止时间顺延等待时长；升级优先级从此刻按新时限重算，降级不延长已有截止时间。
- **权限**：员工侧本部门有效成员即可；IT 台只给 IT 类型部门的有效成员/企业管理员，可见范围限定在同一企业（`scopeTeamIds` 写在已签名路径里，Java 再限定一次）；指派对象必须是 IT 部门的有效成员；**IT 人员不能处理自己提交的工单**，也不能把工单指派给申请人；内部备注申请人看不到。
- **设备台账**：入库 → 领用（可在设备申请工单里直接发放给申请人，自动关联并在工单留痕）→ 归还 / 送修 / 修好（持有人保留）→ 报废（必须先收回）。设备行锁，不会同时领用给两个人；每步写设备事件历史；保修将到期/已过保有标记。
- **AI 整理**：新增工作流 `ticket`（问题描述 → 工单草稿），核对页会带出自助排查建议、分类是否与规则判断一致、是否有同标题未结束工单、名下已有设备等，核对后才保存（幂等键 `automation-{id}`，重复保存不产生第二张）。IT 部门默认选中它。
- **Agent 工具**：员工侧 `search_it_solutions`、`create_it_ticket`、`get_my_it_tickets`、`get_it_ticket_status`、`add_it_ticket_comment`、`get_my_devices`；IT 台只读 `list_it_queue`、`get_it_ticket_detail`、`get_it_desk_summary`、`list_it_devices`。**刻意没有接单/解决/批准/改分类/发放设备的工具**。中央 Agent 现在能把“打印机坏了/忘记密码/申请笔记本”等转给 IT 助手。
- **提醒**：部门负责人——IT 申请等待批准超时（并入审批等待规则）；IT 成员——工单超时/待接单（`it_sla`）；申请人——IT 在等你补充、已解决 48 小时未确认（`ticket_followup`）。
- **效果指标**：服务台汇总给出近 N 天解决数、SLA 达成率、平均首次响应、平均解决耗时、重新打开数，处理人负载；AI 整理的工单进入原有的 AI 工作成果效率统计。

限制（有意不做）：不做按工作日历的 SLA（按自然小时）；已关闭工单不自动归档/评分；设备不对接资产财务；知识条目是内置的 6 条常见问题，没有后台编辑界面；不做 IT 人员排班/自动派单；工单没有附件。

测试：Java `ItServiceDeskIntegrationTest`（14 项，含并发接单/发放）、`tests/test_it_service.py`（权限层）、`tests/test_it_tools.py`、`tests/test_business_checks.py`（工单核对）、`tests/test_work_center.py`（提醒）、`scripts/e2e_it_service.py`（真实端到端 64 项，`--keep` 保留数据供浏览器验证，`--purge` 清理）。

## 人事入转调离（入职 / 转正 / 调岗 / 离职）

流程：人事发起并预检 → 员工所在部门负责人批准 → 自动生成跨部门办理清单（人事 / IT / 财务 / 部门负责人 / 员工本人各办各的，带期限）→ 必办任务全部完成且办结前检查无阻断 → 人事办结 →（调岗、离职）企业管理员落实系统变更。

- **规则检查直接读真实业务数据**：重复/冲突事项（离职办理中不能再调岗）、名下 IT 设备、待审批/草稿报销单、待批请假、离职日之后的已批请假、未休年假、员工是否部门负责人（调走/离职会导致部门无人审批）、新员工有没有假期余额和部门报销预算、试用期是否过短、近 90 天病假。阻断项不处理不能提交；**办结时更严格：离职时设备没收回、报销没结清直接阻断**。
- **权限**：发起、办结只有人事部门有效成员，且不能给自己办；批准只有员工所在部门负责人或企业管理员，不能批与自己有关的、不能批自己发起的；每项任务只能由对应办理方完成（IT 不能替财务办）；可选任务跳过要写原因，必办任务不能跳过。身份（企业范围、办理角色、负责的部门）由 FastAPI 计算并写进已签名路径，Java 只信这三个集合。
- **落实系统变更**：调岗——把员工从原部门移到目标部门；离职——停用员工的企业成员身份（所有部门权限立即失效）。这是改权限的操作，**只给企业管理员**，不能对自己、不能停用企业管理员/所有者。
- **提醒**：部门负责人——人事事项等待批准超时（并入审批等待规则）；各办理方——分给自己的任务 3 天内到期或已逾期（`hr_task`），办完自动关闭。
- **Agent 工具**：所有部门 `get_my_hr_tasks`、`get_hr_case`、`list_hr_cases`；人事模板另有 `precheck_hr_case`（只检查不创建）、`get_hr_summary`。**刻意没有发起/批准/办结/落实变更的工具**。
- **汇总**：各类事项进行中/已办结数量、逾期任务、平均办理天数、待落实的系统变更。

限制（有意不做）：没有考勤打卡数据，转正检查用请假记录代替考勤异常；办理清单模板是内置的，没有后台编辑界面；不生成合同/离职证明文件；新员工账号仍由管理员在企业管理里创建并加入部门，入职事项负责后续办理。

测试：Java `HrCaseIntegrationTest`（10 项，含并发批准只生成一次清单）、`tests/test_hr_service.py`（身份计算与权限、落实变更）、`tests/test_hr_tools.py`、`tests/test_work_center.py`（提醒）、`scripts/e2e_hr_cases.py`（真实端到端 47 项）。

## 跨部门协同办理（中央 Agent 的任务拆分）

一段话里有几件不同部门的事（“下周二请一天年假，报销上周打车费 86 元，另外笔记本蓝屏要报修，还要采购一批办公用品”），在部门工作台“概览”的**跨部门协同办理**里一次拆成步骤：

- **拆分是确定性规则**：按句子、逗号和“另外/还要/同时”等连接词切分，再按关键词归类为请假 / 报销 / IT 工单 / 采购 / 客户跟进 / 人事事项，每步写明“命中了哪些词”；相邻同类合并，没有命中的句子并入上一步作为补充；人事事项后面紧跟的开通账号、配电脑并入人事事项（入职清单本身就含这些 IT 任务，不另开工单）。拆错了可以改类型、改为“不需要”。
- **能不能在本部门办由工作流规则决定**：请假、报销、IT 工单所有部门都能办 → “开始整理”生成一份 AI 工作成果（与单独整理完全同一套权限、额度、核对与保存规则，请求编号由步骤决定，重复点击不会重复整理），整理好直接在下方工作成果面板打开核对；采购只给采购部门、客户跟进只给销售部门 → 标“需其他部门办理”，给出可转交的部门助手；人事事项 → 由人事部门在“人事办理”发起。
- **进度汇总**：计划本身不写任何业务数据，每步状态取自关联工作成果的实时状态（待整理 / 整理中 / 待核对 / 已保存 / 失败），保存后进度自动刷新。
- **从中央助手进入**：中央助手转交时如果问题还涉及其他部门，转交提示里多一个“在部门工作台一次拆成各部门步骤办理”，原话只暂存在本浏览器会话里带过去（不放进地址栏）。

限制：拆分不用模型，复杂口语可能拆不准（可手动改类型）；不会代替用户在其他部门提交，只指明该找谁。

测试：`tests/test_orchestration.py`（拆分与合并规则、按部门判断、改类型/跳过、开始整理关联工作成果且幂等、只能看自己的计划）。

## 部门专业 Agent 自动配置

每个部门按业务类型自动拥有一个主 Agent，管理员不需要再手工创建：

| 部门业务类型 | 自动配置的 Agent | 专业技能（工具） |
|---|---|---|
| 人事 | OA 人事助手 | 请假余额、草稿、提交、审批、进度 |
| 采购 | 采购与库存助手 | 库存、部门预算、采购申请、审批 |
| 销售 | CRM 客户与商机助手 | 客户、跟进、商机 |
| 财务 | 财务报销助手 | 报销预算、报销单、审批 |
| IT | IT 服务助手 | 目前为请假与报销；IT 工单/账号/设备模块尚未上线 |
| 未设置 | 部门办公助手 | 请假与报销 |

- **建部门、修改业务类型、重新启用部门**时自动生成或恢复草稿 Agent，并绑定该 Agent 独立的专业技能；修改业务类型时，旧的已发布 Agent 会退役。
- **停用部门**时，该部门已发布的 Agent 同步退役。
- **发布唯一性按部门**：同一部门同时只能有一个已发布的部门 Agent；不同部门（如销售一部、二部）可各自发布。发布前检查模型是否为可用聊天模型、部门是否启用、Agent 业务方向是否与部门一致。
- 管理后台"组织架构 → 部门管理"选中部门即可看到 **部门专业 Agent** 状态：已发布 / 待发布 / 需要修复（附缺失原因）/ 部门已停用，并提供 **一键修复** 与 **发布给部门员工**。
- 员工在部门工作台能看到部门助手；未发布时显示原因，未连接模型时提示去"设置 → 模型连接"。
- 接口：`GET /admin/org/teams/{id}/agent-status`、`POST .../agent-repair`、`POST .../agent-publish`。迁移 `20261002_0001` 会按存量部门 Agent 回填部门业务类型，并把发布唯一键改为按部门。

## 手工验收

1. **CRM**（销售部门）：选择客户，粘贴 `2026年10月1日与客户沟通，对方希望先试用。约定2026年10月8日发送方案；预算尚未确定。` 检查跟进内容、原文依据、待办日期和疑点，可修改或删除待办；勾选核对后保存，在下方 CRM 模块查看草稿，在成果面板勾选完成待办。
2. **报销**：粘贴 `10月1日出差高铁票260元，发票号G001；出租车48元，暂无发票。` 检查分类、金额、发票号和合计后保存，在报销模块查看草稿。
3. **请假**：粘贴 `我要申请年假，2026年10月12日至2026年10月14日，原因是家庭事务。` 若原文日期不完整，模型留空并提示，补全后才能保存；在"我的请假"查看草稿。
4. **采购**（采购部门）：粘贴含真实 SKU 的需求。填写不存在的 SKU 时，业务系统会拒绝并显示原因（如"未知产品: XXX"），成果退回可修改状态，改正后即可保存。
5. 刷新页面，历史成果和待办状态仍在；其他账号看不到你的成果；退出部门后不能继续访问或保存。
6. Java 服务不可用时，保存结果显示"保存待重试"，内容锁定；恢复后按原内容重试，不会产生重复草稿。

## 保存与重试规则

- 每份成果只有一个固定的 Java 幂等键 `automation-{成果ID}`，首次保存及所有重试都用它。
- **业务系统明确拒绝**（HTTP 400/403/404/422，例如未知产品、客户不存在、字段不合法）：Java 的业务异常会让幂等占位记录随事务一起回滚，这个键下没有任何写入，因此成果退回"待核对"，用户可修改内容后用同一个键重新保存。该不变式由 Java 测试 `rejectedDraft_rollsBackIdempotencyKey_soCorrectedBodyCanReuseIt` 守护。
- **结果不确定**（超时、409 正在处理、5xx）：成果进入"保存待重试"，内容锁定，只允许按原内容重试；若 Java 其实已经写入，重试会拿到第一次的结果，不会重复创建。
- 业务原因（"预算不足"、"未知产品"等）由 Java 的 `ApiExceptionHandler` 返回、Python 原样展示；其它异常只显示通用说明，不暴露内部信息。

## 实现与边界

- 原文、模型输出、核对后内容、业务结果、耗时及 Token 用量保存在 MySQL `automation_work` 表；月度额度统计包含这些调用。
- 模型输出必须通过严格 schema 和原文依据校验：每条 evidence 必须逐字出现在原文中，金额、日期、数量有格式校验，同批发票号和 SKU 不能重复，模型不能附加价格或提交指令。
- 支持粘贴及 UTF-8 TXT/Markdown/CSV 导入，最多 15,000 字；费用仅支持人民币。不包含图片/PDF OCR、凭证过账或自动付款。
- 材料密级为"受限"时禁止调用模型；"机密"只能用受信任模型。
- 待办属于当前用户的工作成果，不会自动分派、发邮件或推送提醒。
- 生成超时 90 秒；进程中断留下的"整理中"记录超过 3 分钟后会被标记为失败，可带回原文重新整理。
- 统计展示处理、保存、失败、修改数量和实际整理耗时；没有把模型耗时包装成"节省的人工时间"。
