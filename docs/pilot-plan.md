# 试点方案：用真实数据证明“有没有提效”

目标：找 5–10 位真实员工用 2–4 周，回答三个问题——**用不用**（采纳）、**好不好**（质量与满意度）、**省不省时间**（对比手工办理的实测时间）。系统已经内置了采集这些数据的功能，这份文档说明怎么组织。

## 零、先跑预检（开始前 10 分钟）

```powershell
.venv\Scripts\python.exe scripts\pilot_preflight.py --org <试点企业编号>
```

它和演示就绪检查（`/system/readiness`）不是一回事：**试点必须用真实模型**（离线演示模型是规则抽取，会让采纳率和节省工时都失真），而且要有备份、没有堆积的死信、参与的人都连了模型、部门有业务类型和负责人、有人事成员、考勤的工作日历录过。输出里 **FAIL 必须先处理**（退出码 1），WARN 是你需要知道的风险。加 `--md` 可输出 Markdown 表格，贴进试点记录留档。

## 一、选人与分工

- 5–10 人，覆盖 2–3 个部门；至少包括：每天要办报销/请假/工单的普通员工、一位部门负责人（看审批与责任协同）、一位财务或 IT 人员（看凭证与工单）。
- 不选“最熟悉系统的人”，否则采纳率会被高估。
- 试点范围要覆盖三类功能，每类至少有人真实用到：**AI 整理工作成果**（报销、请假、工单、客户跟进…）；**责任协同**（一份真实的会议纪要 → 责任事项 → 接受 → 提交 → 验收，需要一位负责人和一位验收人）；**考勤异常**（需要一位人事成员导入一个月的真实考勤文件，员工说明、负责人认定）。
- 明确一位试点负责人，每周看一次报告、收集口头反馈。

## 二、开始前（第 0 天，约 30 分钟）

1. 管理员建好企业、部门、账号，给每位试点员工连接模型（或统一用企业模型）。真实模型的提取质量与离线演示模型不同，**试点必须用真实模型**。
2. 管理后台“AI 工作成果”里确认各类工作的手工办理基准是否合理——这只是**临时值**，下面第 3 步的实测样本够了就会自动取代它。
3. 告知试点员工三件事（见第五节“告知与隐私”）。
4. 每人做一次“手工计时”：下次**不用 AI** 办一件同类事（报销、请假、工单…），自己计时，在 AI 整理页面保存成果后评价里填“这件事手工做大约要多久”；或用同事的实际经验。**每类工作至少 5 个样本、来自至少 3 个人**，系统才会采用实测中位数；不够就继续用设定值，报告里会写明。

### 第 0 天还要做的两件事（人事和负责人）

- **人事**：在“考勤 → 规则与日历”录入本年度节假日和调休（每行 `日期,类型,备注`，类型写 上班 / 休息 / 节假日），确认各部门上下班时间和迟到宽限；然后导入一份**真实的**上月考勤导出文件（打卡机 / 钉钉 / 企业微信的 `.xlsx` 或 `.csv`），对不上的名字一次性选好对应关系。没录日历就分析，节假日会被当成上班日，产生大量旷工误报。
- **负责人**：确认部门成员、业务类型、负责人设置对（预检会提示缺什么）。

## 三、试点期间

- 每天正常工作，优先用“让 AI 帮我整理工作”处理材料，保存前一定核对。
- 每份成果保存后，花 10 秒评分（1–5）、写一句话（可不写）。差评比好评更有价值。
- 遇到出错，把页面上的**问题编号**（形如 ISSUE-20261007-0012）发给试点负责人；管理员在“问题中心”处理。
- **责任协同**：把真实例会纪要粘贴进“责任协同 → 文本整理”，负责人核对（补责任人、期限、验收标准）后发布；员工在“我的责任”里接受或提异议；验收人对照验收标准验收。每个人至少完整走一遍，并留意哪一步卡住。
- **考勤异常**：人事每周导入新的考勤文件并点“开始分析”；员工看到提醒后在“考勤”里写说明；负责人和人事认定。只统计流程有没有跑通，**不用它评价任何人的考勤**。
- 每周一，试点负责人运行：

```powershell
.venv\Scripts\python.exe scripts\pilot_report.py --days 7
```

得到 `docs/pilot-report-日期.md`。

## 四、怎么看报告（以及不能怎么看）

| 指标 | 看什么 | 注意 |
|---|---|---|
| 采纳率 | 保存过成果的人 / 部门成员 | 低于 50% 先问原因，不是人的问题 |
| 重复使用人数 | 用了 ≥2 次的人 | 比“试用过”更能说明有用 |
| 保存率 / 一次通过率 / 平均修改比例 | AI 的结果有多少被直接采用 | 修改多的类型是改进重点 |
| 估算节省工时 | 基准 − AI 办理耗时 | **只有基准来源是“员工实测中位数”时才可信**；“系统默认值”只是估算 |
| 评价 | 平均分、分布、匿名评语 | 少于 5 条没有代表性 |
| 可靠性 | 失败率、未关闭问题、恢复时间、页面脚本错误涉及的问题数 | 失败率高先看错误码，往往是模型配置而不是代码；页面错误在问题中心里服务名是 web-frontend |
| 考勤异常处理流程 | 员工说明率与中位说明时长、认定率与中位认定时长、补录后系统自己消除的比例 | 说明流程有没有跑通，**不评价考勤本身**；异常多少取决于导入的文件和规则；少于 10 条时没有代表性 |
| 责任协同 | 部门工作台“责任协同 → 部门看板”（负责人看）：接受责任的中位时间、按时提交率、首次验收通过率 | 数据在 Java 业务服务里，试点报告暂未汇总；每周请负责人截图附在记录里 |

报告里**没有**个人排名、没有按人展开的数据，也不要自己去拼——试点是为了判断产品是否好用，不是考核员工。

诚实的结论格式：“在 N 位员工、M 份成果、实测基准的前提下，每份报销平均节省约 X 分钟，一次通过率 Y%，评价 Z 分；样本量/部门范围有限，结论仅限于这些场景。”样本少于 30 份、评价少于 5 条时，报告会自己提醒。

## 五、告知与隐私

给试点员工的说明（可直接转发）：

1. 系统只统计“用了多少次、保存了多少、改了多少、花了多久”，评价和计时只汇总展示，**不显示你的名字**；
2. 你整理的材料会发给公司配置的模型服务（按材料密级，受限材料不能整理）；报告里不含材料内容；
3. 这是在评估系统，不是评估你；不想记录手工计时可以不填。

## 六、怎么判断试点成不成功

下面是**建议的起点，不是定论**，请按公司情况调整并在试点开始前就写下来，避免看到结果后再挪标准：

| 结论 | 建议条件（同时满足） |
|---|---|
| 值得扩大 | 采纳率 ≥ 50% 且重复使用的人 ≥ 一半；一次通过率 ≥ 60%；基准是员工实测、且每份平均节省 > 0；评价平均 ≥ 3.5 且不少于 5 条；两周内没有未处理的高/严重问题 |
| 先改再试 | 采纳率或通过率不达标，但差评集中在 1–2 类工作或 1–2 个具体问题上（改进清单能列出来） |
| 暂缓 | 失败率高且原因不是模型配置；或权限、数据泄露类问题出现过 |

样本少于 30 份成果、评价少于 5 条时，无论数字好坏，结论都只能写成“初步观察”。

## 七、试点结束后

- 导出最后一份 30 天报告存档；
- 把“实测基准”留着：它已经替代了设定值，之后的节省工时都按它算；
- 把评语里反复出现的问题列成改进清单，按“出现次数 × 影响”排序，下一轮迭代先做前三项。

## 八、系统里相关的位置

| 功能 | 位置 |
|---|---|
| 评分、手工办理时间、一句话评价 | 成果保存后，AI 整理面板里的“这次整理好用吗” |
| 效果指标与基准 | 管理后台 → AI 工作成果（基准来源标注：实测 / 管理员设定 / 默认） |
| 试点报告 | `GET /admin/pilot-report?days=30&team_id=…&format=md`，或 `scripts\pilot_report.py` |
| 出错与恢复 | 管理后台 → 问题中心（含 Agent 运行可靠性、死信队列） |
| 开始前预检 | `scripts\pilot_preflight.py --org <企业编号> [--md]`（真实模型、备份、死信、成员模型连接、部门与负责人、考勤日历） |
| 考勤异常 | 部门工作台 → 考勤（员工：我的考勤；负责人：部门异常；人事：全员异常、导入与分析、规则与日历） |
| 责任协同 | 部门工作台 → 责任协同（部门看板给负责人） |
| 页面脚本错误 | 管理后台 → 问题中心，服务名 web-frontend |
