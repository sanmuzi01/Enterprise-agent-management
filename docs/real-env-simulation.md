# 仿真联调：没有真实应用时，怎么在“接近真实”的环境里验证飞书 / 钉钉接入

真机联调需要两样东西：公网 HTTPS 地址、在飞书 / 钉钉开放平台建好的测试应用。没有它们之前，用**开放平台仿真器**
在 Docker 里把整条链路跑一遍——除了“飞书 / 钉钉服务器本身”是仿真的，其他都是正式部署的样子：

```
仿真器（扮演飞书 / 钉钉服务器）──签名加密的回调──▶ nginx（web）──▶ api ──▶ MySQL / Redis / Chroma / Java 业务中心
        ▲                                                   │                     worker（定时任务）
        └──────── 平台调开放接口：换令牌、发消息、查姓名、取聊天记录…… ◀──┘
```

- 平台是 `docker compose` 起的整套（和交付给客户的一样），请求都经 nginx，Host 白名单、Cookie + CSRF 登录都是真的。
- 仿真器（`deploy/simulator/platform_simulator.py`）**按飞书 / 钉钉文档独立实现**签名和加密，不引用平台的代码——
  两边各写一遍还能对上，才说明平台的实现和文档一致。
- 联调脚本（`deploy/simulator/run_scenarios.py`）按真实上线的顺序操作：管理员在后台配置 → 开放平台校验回调地址 →
  员工在设置页领绑定码、在飞书里发给机器人 → 对话 → 聊天进 CRM → 通知推送 → 平台故障与恢复 → 钉钉 → 员工离职。
  员工用演示数据里的账号；管理员是脚本临时建的，结束删除。

## 怎么跑

用独立的项目名 `-p agentsim`：容器和数据卷都和平时的 `docker compose` 分开，**不碰你已有的数据和真实的飞书配置**。
两套用的主机端口一样（8011 / 8080 / 18090），先把平时那套停掉（`docker compose stop`）。

```bash
docker compose -p agentsim -f docker-compose.yml -f docker-compose.simulate.yml up -d --build
docker compose -p agentsim -f docker-compose.yml -f docker-compose.simulate.yml exec api python scripts/seed_enterprise_demo.py
docker compose -p agentsim -f docker-compose.yml -f docker-compose.simulate.yml exec platform-sim python /sim/run_scenarios.py
docker compose -p agentsim -f docker-compose.yml -f docker-compose.simulate.yml down -v
```

在 Windows 的 Git Bash 里，`/sim/...` 会被改写成 Windows 路径，前面加 `MSYS_NO_PATHCONV=1`（PowerShell 不用）。
脚本发现库里已经有飞书 / 钉钉配置就不运行（不覆盖），结束时删除它建的接入配置、绑定、事件记录、群记录、CRM 活动和测试通知。

## 2026-10-10 这次的结果：52 项通过，0 项失败（63 秒）

| 环节 | 验证了什么 | 结果 |
|---|---|---|
| 管理员接入（飞书） | 后台保存凭证并启用；“测试连接”换到 tenant_access_token；开放平台保存回调地址时的加密校验（url_verification）；接入自检各项 | 9 项通过；“公网 HTTPS”一项按预期未通过（仿真环境没有） |
| 回调安全 | 签名错、内容被篡改、1 小时前的请求、抓包重放（同一个 nonce）都被拒绝（401） | 4 项通过 |
| 员工绑定 | 没绑定的人收到绑定步骤；两名员工在设置页领码、私聊机器人绑定成功、设置页显示已绑定和飞书姓名；绑定码发在群里被拒绝 | 8 项通过 |
| 对话 | 私聊提问由助手回答（0.5 秒）；飞书重推同一事件只处理一次；群里没 @ 机器人不回复 | 3 项通过 |
| 聊天进 CRM | “保存到CRM：”对上客户；合并转发 3 条记录对上客户、重发不重复；普通销售不能开启整群记录、负责人开启后群里公告；撤回的不算；整理成群聊活动；三个客户的时间线在网页上都能看到；没开启的群不进 CRM；网页上看到并关闭，机器人在群里告知 | 13 项通过 |
| 通知推送与故障恢复 | 业务通知 1 秒内送到飞书；飞书不可用时进入重试、后台显示“重试中”、站内通知照常；恢复后 21 秒自动补发 | 4 项通过 |
| 钉钉 | 保存凭证、测试连接、事件订阅校验（check_url 加密应答）；私聊绑定；对话经 sessionWebhook 回复；同时绑定两边的员工两边各收到一条通知（钉钉经机器人单聊批量发送） | 6 项通过 |
| 员工离职 | 飞书推送离职事件后绑定立即停用，再发消息用不了助手 | 1 项通过 |

**这次仿真发现并修好的问题**：演示数据脚本（`scripts/seed_enterprise_demo.py`）在已有企业的库里会再建第二家企业。
平台只服务一家企业（id 最小的那条），全新部署启动时已经自动建好了“默认企业”，演示账号却都在第二家企业里，
结果飞书 / 钉钉绑定这类企业级功能对演示账号全部不可用（“你不是本企业的有效成员”）。现在已有企业时演示部门和账号放进这家企业。
单元测试发现不了这个问题：测试库里用户和企业是测试自己建的，只有在“全新部署 + 演示数据”的真实组合里才会出现。

**仿真中看到但不算失败的**：飞书不可用期间员工发来的消息，回调照常应答、记为“处理失败”（后台接入页能看到），
机器人的回复不会补发——这是设计如此（对话是即时的，过时的回复补发没有意义），员工恢复后再问一次即可。

## 仿真不了的：真机联调时逐项确认

| 项 | 为什么仿真不了 | 怎么确认 |
|---|---|---|
| 公网 HTTPS、证书、穿透 / 反向代理 | 仿真器在容器网络里直连 nginx | `scripts/check_integration_callback.py feishu` 通过；后台接入自检全部打勾 |
| 飞书 / 钉钉服务器的真实行为 | 仿真器是按文档写的，文档没写清的地方两边可能一起错 | 下面每一项真机走一遍 |
| 开放平台的权限审核、版本发布、可用范围 | 只在开放平台后台 | 应用已发布、可用范围包含试点员工；权限：收发消息、通讯录基本信息、手机号；整群记录另需“获取群组中所有消息”“获取群组信息” |
| 钉钉互动卡片回调的签名 | 钉钉文档说明不完整 | 配卡片模板后真机点一次“确认执行” |
| 一键授权（OAuth） | 授权页在 accounts.feishu.cn / login.dingtalk.com，要真实浏览器登录 | 设置页点“用飞书授权绑定”，授权后跳回显示已绑定 |
| 合并转发子消息的发送人 | 外部联系人在真实飞书里能否查到姓名 | 转发一段和客户的聊天，看客户显示为“外部成员 1”还是真名 |
| 群消息推送 | 应用要开“获取群组中所有消息”才会推 | 开启整群记录 10 分钟后网页上“已记录”条数在增加 |
| 真实大模型的回答质量 | 仿真用的是离线演示模型（只能整理固定几类材料） | 在设置里连接真实模型，试点员工用两周 |
| 消息频率限制、大群、长消息 | 仿真器不限流 | 试点期观察后台“处理失败”和“重试中”的数量 |

真机联调步骤见 [collaboration-integrations.md](collaboration-integrations.md) 的“真机联调步骤”。
