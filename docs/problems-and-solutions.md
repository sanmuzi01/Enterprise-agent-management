## 1. 部署到阿里云服务器（2026-09-16 起）

| 问题 | 原因 | 解决 |
|---|---|---|
| 服务器系统是 CentOS 7 | 2024 年 6 月已停止维护；装 Python 3.11 还得自己编译 | 服务器上还没有数据，直接在控制台换系统盘，改成 Alibaba Cloud Linux 4 |
| 用 `curl` 装 nvm 超时，接着报 `nvm: command not found` | 国内访问 raw.githubusercontent.com 不稳定 | 不用 nvm，改用 dnf 装 Node；npm、pip 换国内源；最后整体改用 Docker 部署 |
| 镜像加速器地址写成了 `https://https://xxx.mirror.aliyuncs.com.mirror.aliyuncs.com` | 前缀和后缀各多拼了一遍 | 改成 `https://qwu9x0mi.mirror.aliyuncs.com`，再用 `docker info` 核对 |
| `docker pull redis:7-alpine` 报 not found，`hello-world` 却能拉下来 | 阿里云的免费加速器只缓存热门标签，带具体版本号的标签基本拉不到 | Redis 改用 `redis:alpine`。`python:3.12-slim`、`chroma:1.5.9`、`mysql:8.0` 走 DaoCloud 代理（`docker.m.daocloud.io/...`）拉取，再用 `docker tag` 改回原名 |
| 用 Xftp 上传后，服务器上缺 `utils/`、`docker-compose.prod.yml`、`.env.production.example` | 漏选；以点开头的文件是隐藏文件，Xftp 默认不显示 | 本地和远程都打开“显示隐藏文件”再补传，用 `ls -la` 核对。不要上传 `.venv`、`node_modules`、本地的 `.env` 和日志 |
| `cp .env.production.example .env` 停在 `overwrite?`，后一条命令被当成了它的回答 | root 用户的 `cp` 默认是 `cp -i`，覆盖前会询问 | 先按 Ctrl+C 退出；要覆盖时用 `cp -f` |
| 在容器里用 pip 装 cryptography 超时 | 默认访问国外的 PyPI | 加上 `-i https://mirrors.aliyun.com/pypi/simple/`；compose 增加 `PIP_INDEX_URL` 构建参数 |
| `nano: command not found`；进了 nano 的帮助界面不知道怎么退出 | 精简版系统没装 nano | 用 `dnf install nano` 安装，或改用 vi。Ctrl+X 退出，Ctrl+O 保存 |
| `.env` 里一直是模板占位值（`change-me-...`） | 中途换了话题，之前的修改没有真正生效 | 用 `sed` 一条条替换，改完用 `grep -v '^#' .env` 核对 |
| 没有买 RDS | 部署方案默认用云数据库 | compose 增加自建的 MySQL 容器 `db`，配置改为 `DB_HOST=db`、`REDIS_URL=redis://redis:6379/0` |
| 网站地址给成了 `sanmuzi.asia.com` | 那是域名注册商停靠页的链接，不是你的域名 | 在控制台确认真实域名是 `sanmuzi.asia`，添加 `@` 和 `www` 两条 A 记录；证书签好之前先关掉 HSTS |
| 部署上线后，技能管理里看不到之前导入的 75 个技能 | 那次只导入了本机数据库，线上是另一套库，数据不会跟着代码上线 | 网页上传技能包，或在服务器上运行 `scripts/import_skill_pack.py`（c6f7443） |
| nginx 对这个项目有没有用？ | — | 必须要：它托管前端、反向代理 `/api`、提供 HTTPS、加安全响应头。顺带发现限流拿不到用户的真实 IP，全站共用一份额度，已修（daf3551） |

## 2. 本机运行与开发环境

| 问题 | 原因 | 解决 |
|---|---|---|
| 启动后端报 `WinError 10013` | 8011 端口被之前验证时留下的后端进程占着 | 先关掉旧进程；用 `netstat -ano \| findstr :8011` 查看是谁占着 |
| 后端连不上 | 8011 上同时挂着两个后端，旧的那个卡死了，请求随机落到它身上 | 杀掉旧进程；以后遇到先查端口 |
| 本机到底要启动几个进程？ | 完整项目要 4 个：后端、Worker、Java 业务服务、前端；文档只写了前 3 个 | 补全文档；Java 服务的启动命令直接从 `.env` 读数据库账号 |
| 运行 Java 启动命令报错，`cd D:\...` 提示 No such file | 你用的是 Git Bash（提示符显示 MINGW64），而给的是 PowerShell 写法 | 给了 Git Bash 写法，路径要写成 `/d/PyCharm/...` |
| Worker 一屏屏报“企业业务服务连接失败、熔断打开” | Java 服务还没启动 | Java 服务启动后，熔断 30 秒内自动恢复，不用重启 Worker |
| 改了代码，页面没变化 | — | 前端是热更新，按 Ctrl+F5 刷新即可；后端带 `--reload` 会自动重启；Worker 不会自动重载，要手动重启 |
| DeepSeek 报 `Authentication Fails, api key invalid` | 配置的 Key 已经失效 | 在“模型连接”里换成有效的 Key；没有可用模型时，组件返回中文提示，不会崩溃 |
| 5173 被旧进程占着，或者 `localhost` 解析到 IPv6，看着启动了，页面却打不开 | — | 前端固定用 `127.0.0.1:5173` 并开启 `strictPort`，端口被占就直接报错（274978e） |
| 本地 MySQL 没启动时，每个测试模块都要等 20 秒超时，看起来像卡死 | 每个模块各自探测一次数据库 | 整个进程只探测一次，先做 1.5 秒的端口探测；失败时直接给出启动测试库的命令（ec476a9） |
| PATH 里的 python 没有数据库驱动 | — | 统一用 `.venv\Scripts\python.exe` |
| Bash heredoc 吞掉反斜杠，中文引号报错 | — | 改文件一律用编辑工具，改完用 grep 核对 |
| Git Bash 把 `/sim/...` 当成 Windows 路径自动转换 | — | 命令前加 `MSYS_NO_PATHCONV=1` |

## 3. Docker

| 问题 | 原因 | 解决 |
|---|---|---|
| 报 `failed to connect to the docker API ... dockerDesktopLinuxEngine`；有一次 Docker Desktop 打开后自己又关掉了 | Docker Desktop 没有启动；第一次运行需要在界面里同意协议、登录，或处理 WSL 的提示 | 手动打开 Docker Desktop，处理完提示，等引擎就绪 |
| 第一次构建要下载 torch 和 CUDA，1.5GB 以上 | 依赖里默认装的是 GPU 版 torch | 开发阶段先不用 Docker（2703059）；后来恢复 Docker，并让各个依赖都能配置国内源（88514f8） |
| 构建时 `apt` 失败，`exit code: 100` | 第一次是 PowerShell 里用 `$env:` 设的镜像源变量，换了窗口就丢了；第二次是阿里云、清华、中科大的 Debian 源都返回 502 | 用 `docker compose config \| findstr MIRROR` 确认变量已生效；起临时容器逐个测试镜像源，换成华为云 `repo.huaweicloud.com` |
| `npm ci` 下载 zrender 时报 `ECONNRESET`，并把其他正在构建的服务也取消了 | 网络偶发断开；compose 默认几个服务并行构建，互相抢网速 | 一个服务一个服务地构建，哪个失败就单独重跑 |
| Java 镜像构建了 19 分钟 | Maven 下载依赖慢；`dependency:go-offline` 还会额外下载大量插件 | 去掉 `go-offline`，改用 BuildKit 缓存 Maven 仓库（88514f8） |
| Chroma 容器永远是 unhealthy，api 起不来 | 镜像里没有 curl 和 wget | 健康检查改成用 Bash 检查端口（88514f8） |
| 端口冲突 | Windows / Hyper-V 保留了部分端口 | Java 的主机端口改用 18090（88514f8） |
| Docker Desktop 自带的 AI 助手擅自改了 `Dockerfile`、`.dockerignore`、compose | 它自己开了一个会话“帮你容器化”，和我同时改同一批文件 | 先把它停掉，再把这几个文件还原到测试过的版本 |
| 容器里跑的不是最新代码 | 代码是在构建镜像时复制进去的，没有挂载本机目录 | 运行 `docker compose up -d --build` |
| 出现了 `agentsim` 和 `pythonproject1` 两组容器 | `agentsim` 是仿真联调用的临时环境，和平时那组用同一批端口 | 用完执行 `down -v` 删除，再切回 `pythonproject1`；以后仿真环境改为不占主机端口（`ports: !reset []`） |
| 用 Docker 会不会影响本机环境 | — | 不会：容器里的 MySQL 数据在 Docker 卷里，和本机库无关。但端口有重叠，两套不要同时开 |
| 知识库向量一重建容器就丢，备份出来的包只有 105 字节 | Chroma 1.x 的数据在 `/data`，compose 却挂到了 `/chroma/chroma` | 改挂 `/data` 并迁移已有数据；备份时发现目录为空就直接失败（5aae2fb） |
| 部门助手的技能文件、提示词，重建容器就丢 | 运行时目录没有挂数据卷；之前能用，是因为开发机上的文件被打进了镜像 | 运行时目录全部放进数据卷；`.dockerignore` 排除这些目录；加测试检查 compose 是否挂全（ee9f18e、5aae2fb） |
| 同时启动所有服务，内存紧张时进程被系统杀掉 | — | 演示脚本改成依次启动，并等每个服务就绪（2e08db5） |
| `/health` 永远返回 200，坏掉的实例照样接流量 | 健康检查不查依赖 | 拆成 `/live` 和 `/ready`（ec476a9） |

## 5. 权限与越权

| 问题 | 原因 | 解决 |
|---|---|---|
| 审批 / 拒绝工具谁都能用；能看、能批别的部门的申请（P0） | 工具写死了审批权限；Java 按 id 查单，不看部门 | 管理员身份按真实角色计算后签名；Java 新增 `TeamAccessGuard` 做资源级校验；越权一律返回 404（0c7c490） |
| 跨企业提权：企业 B 的管理员能批企业 A 的请假、看 A 的 IT 工单 | 签名里的管理员标记不区分企业 | 按资源所属企业重新计算；签名带上企业部门范围；平台审批也只对资源所在企业可见（e9fdd1f） |
| 停用部门或企业后，成员权限完全不受影响（P0） | 鉴权 SQL 只查成员表的状态，没有检查部门表、企业表的状态 | 所有成员和角色判断都加上部门、企业 `status='active'`（824e3f4） |
| 员工被移出企业后，残留的部门成员记录仍能用部门助手、做审批 | 部门权限不看本人的企业成员身份 | 部门成员判断统一要求：部门有效、企业有效、本人企业身份有效（2198a37） |
| 任何部门的成员都能调用采购和 CRM 接口 | 接口不校验部门的业务类型 | 新增 `department_access.py`：采购只给采购部门，CRM 只给销售部门，请假和报销全员可用（2198a37） |
| 管理员能借部门助手的部门身份，往部门里写数据 | 工具直接取助手所在的部门 | 只有调用者是该部门有效成员或企业管理员时才采用（2198a37） |
| 一人管两个部门时取错部门 | 固定取“在职的第一个部门” | 优先用部门助手自己的部门（0e738d0） |
| 普通用户能把自己的助手声明成中央或部门助手 | `POST /agent` 接受客户端传来的类型 | 类型只能在企业管理后台由服务端计算（0e738d0） |
| 普通用户能给助手配任意外部 HTTP 接口 | 接口工具只要求登录 | 默认只有管理员能配，开关是 `FEATURE_USER_API_CONNECTORS`（2ce40df） |
| 草稿或已退役的部门助手、技能仍能被直接使用（P0） | 发布状态只在“路由挑选”时查过一次 | 收口到唯一的权限入口 `get_usable_agent`；技能每次加载都重新检查；编辑已发布的技能会自动打回草稿（c8b6069） |
| 平台审批可以自己批自己，还可能被并发重复消费（P0） | 角色门槛挡不住“申请人本身就是管理员”；消费是先查后改 | 禁止自审批；消费改成条件 UPDATE（824e3f4） |
| `/health` 不用登录就能看到连接池、熔断器等内部细节 | 健康检查和诊断混在一起 | `/health` 只返回布尔值；完整诊断移到需要登录的 `/system/diagnose`（612279d） |
| 责任协同里的验收人、主责人、指派人权限混乱 | — | 定下硬规则：指派只有负责人能做；接受、提交只有主责本人能做；验收人不能是主责人（06281c7） |

## 6. 并发与一致性

| 问题 | 原因 | 解决 |
|---|---|---|
| 并发审批同一张请假单 8 次全部成功；两张单同时批会把预算花两遍 | 没有行锁 | 请假单与余额、采购单与预算、报销预算都加悲观写锁（e9fdd1f） |
| 同一张报销单被两个审批人并发批准，重复扣预算 | 没有行锁 | 审批加行锁；回归测试在去掉锁时会失败（eee129b） |
| 企业可能被并发操作降到零个所有者 | 先查数量再修改（TOCTOU） | `SELECT … FOR UPDATE` 锁住全部在职所有者这个固定集合；先确认测试在修复前会失败（ff82e2a） |
| 并发申请会出现重复的审批单；两人同时决定会互相覆盖 | 先查后插，先读后写 | 用唯一约束 `active_dedupe_key` 兜底；决定改成条件 UPDATE，后到的返回 409（9b4e1e7） |
| 审批已被消费，业务却没执行成功，资源卡死 | “消费”和“执行”分在两个事务里；审计函数里还藏着一次提前 commit | 两步放进同一事务；把审计挪到真正提交之后（39449f9） |
| Java 幂等：两个并发请求都执行了，外部系统被调用两次 | 先查记录再执行 | 抢占式插入占位记录，插不进去直接返回 409（dda008f） |
| 同一个部门可能有两个已发布的助手抢着回答 | 没有唯一约束 | 加 `department_publish_key` 唯一索引，后来改为按部门（`t{team_id}`）唯一（9032e55、67e76dd） |
| 高风险工具的同一个确认 token，并发点两次会执行两遍 | — | 条件 UPDATE：`WHERE status='pending'`（4df7b1c） |
| 多实例下，同一个事件被处理两次 | 先查收件箱再插租约，不是原子操作 | 拿到租约后再确认一次收件箱（e7e34d5） |
| Redis 并发配额上限设 5，实际放行了 13 个 | 多次往返，不是原子操作 | 改成一个 Lua 脚本（168f7ff） |
| Redis 首次连接时出现竞态，限流被突破成 2 倍 | 其他线程在“重试窗口”内拿到 None，退回进程内限流 | 连接加锁；只有真正连接失败后才开启重试窗口（168f7ff） |
| 首次启动自动建企业，多个实例可能建出好几家 | 没检查 `GET_LOCK` 的返回值 | 检查返回值，再加哨兵表 `bootstrap_marker` 的主键兜底。反向验证：去掉哨兵后，6 个线程建出了 6 家企业（5c34b3b） |
| 乐观锁可以被绕过 | 版本号参数是可选的；只改 Prompt 或配置时不递增版本 | 编辑接口的版本号改为必填；单独改配置也递增版本（1e9edc3） |
| IT 文章的“打开”和“评价”请求同时到达，报 500 | 撞了唯一约束 | 改用 `INSERT … ON DUPLICATE KEY UPDATE`（15855a2） |
| Java 并发幂等测试间歇性失败 | 断言写死“一个 200、一个 409”，没考虑合法的缓存重放；当时还有一个残留的 Java 进程在抢同一个库 | 断言改成真正的不变式：只建出一条草稿；关掉残留进程（2198a37） |

## 7. 注入与攻击面（安全专项测试）

| 类别 | 发现的问题 | 解决 |
|---|---|---|
| SSRF | 跟随重定向能绕过校验，还会把 API Key 带出去；阿里云元数据地址 `100.100.100.200` 不算内网；`2130706433`、`0x7f000001` 这类数字 IP；DNS 重绑定 | 全部禁止重定向；只放行全球可路由的地址；自己解析数字 IP；校验过的解析结果固定 30 秒；19 项攻击载荷矩阵测试（2860e34） |
| 恶意文件 | 400KB 解压成 400MB 的压缩炸弹；技能包用 Windows 盘符、UNC、设备名做路径逃逸；附件名叫 `con.txt` | 统一用 `archive_guard.py`：解压前先体检，文件名检查加真实路径包含检查（7006291） |
| SQL 注入 | 没有发现注入；但顺带发现新用户第一次保存个人画像必然 500 | 静态守卫，加上对约 250 个路由的自动模糊测试；修复画像保存时传错的参数（e3f8252） |
| XSS | 脚本类载荷都已被挡住，但模型仍能输出钓鱼表单、全屏覆盖层，或用外链图片零点击泄露对话内容 | 禁用表单和媒体标签，禁用 `style`、`id`、`name` 属性；外部图片改成链接；在真实浏览器里验证了 79 个载荷（cd19051） |
| 提示注入 | 文档里的指令诱导模型调用工具；伪造“资料结束”分隔符和来源编号；深层嵌套的 JSON 让服务 500 | 高风险工具必须用户确认；身份只来自服务端；`prompt_guard.py` 让伪造的分隔符失效；嵌套 JSON 一律当作“结果不可用”（d0e438d） |
| 数据外发 | 机密、绝密资料会原样发给外部云模型 | 检索结果进提示词之前按密级拦截：绝密一律拒绝，机密只发给白名单里的模型（42ce426） |
| 会话 | 令牌存在 localStorage，也没有 CSP | 改为 HttpOnly Cookie，加上与会话绑定的 CSRF；Nginx 下发 CSP（168f7ff） |
| 缓存 | Redis 里的缓存用 pickle 反序列化；缓存里放着解密后的 API Key | 只用 JSON；只缓存密文（168f7ff） |
| 上传 | 没有大小上限；分块读进来后仍整块放在内存里 | 分块直接写临时文件；单文件、单次请求、并发数都有上限；没有权限的请求一个字节都不收（168f7ff、ec476a9） |
| 请求签名 | 签名不包含方法、路径和请求体，截获后能换个接口重放 | 方法、路径、请求体哈希一起签名；请求体按固定的字节序列化（dda008f） |
| 真实 IP | 在 nginx 后面，所有人共用同一份 IP 限流额度 | 只信任内网代理带来的 `X-Forwarded-For`（daf3551） |
| 登录 | 有明文口令兜底；会区分“用户不存在”和“密码错误” | 只接受 bcrypt；统一返回 401；改密码或强制下线后旧令牌立即失效（6946491、49ab5cd、f232d93） |
| 短信验证码 | 换号码、换 IP 就能刷，短信费用没有上限 | 全站封顶，并限制校验和重置密码的频率（c319b3a） |

## 18. 反复出现的规律（面试可以总结成方法论）

1. **先查后改都不安全**：审批、幂等、所有者保护、配额，最后都改成了条件 UPDATE、唯一约束、行锁或 Lua 原子脚本。
2. **权限只在入口查一次不够**：发布状态、技能绑定、部门身份，都要在每次真正使用时重新检查。
3. **有些 bug 只在全新环境才暴露**：空库里没有企业、空库的 id 从 1 开始、空库迁移报漂移。所以把空库测试接进了发布自检。
4. **“不报错但悄悄降级”最危险**：审计账号是空字符串、连接串解析错、备份是空包、助手显示“已就绪”却没有工具。办法是启动时校验、备份失败就退出、状态检查读真实文件。
5. **修复要先证明测试会失败**：大部分回归测试都做过反向验证，去掉修复后失败，加上修复后通过。
6. **单元测试抓不到接线错误**：浏览器里点“保存”报 500、span 全部被丢、提醒规则连续失败上百次，都是在真实浏览器、真实容器、真实数据上才发现的。
7. **国内网络是部署的常态问题**：GitHub、Docker Hub、PyPI、npm、Debian 源都可能不通。提前准备镜像源，构建参数可配，失败时先用小测试确认是哪个源的问题。
8. **多个进程、多个助手同时操作同一份资源会出事**：多个后端同时建表、两个后端抢同一个端口、两个 AI 同时改同一批文件、残留的 Java 进程搅乱测试。动手前先确认现场只有自己在操作。
