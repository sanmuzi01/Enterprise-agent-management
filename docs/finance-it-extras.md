# 财务与 IT 补齐

## 发票识别（`service/invoice_parser.py`、`service/invoice_service.py`）

报销填表时“识别发票”：上传 PDF / 图片 → 识别字段 → 校验 → 员工核对确认 → 发票号、金额带进报销明细。

**每个字段都有置信度**，不是模型自报的，而是按来源和校验算的：

| 情况 | 置信度 |
|---|---|
| 文字版 PDF，按标签（“发票号码：”“（小写）”……）取到 | 0.95 |
| 图片 / 扫描件经 OCR 后按标签取到 | 0.80 |
| 只能按位置推断（没有“购买方 / 销售方”标记） | 0.70 |
| 格式校验不过、金额对不上、重复 | 0.40 |

低于 0.90 的字段必须员工逐项确认（勾“已核对”或直接改正，改过的记为人工填写）；**没确认的发票不能用于报销**。
文字版发票所有字段高置信度、校验全过时自动确认。

校验：发票号码格式（全电 20 位无代码 / 传统 8 位 + 10 / 12 位代码）、税号（18 位统一社会信用代码按 GB 32100 算校验码）、
金额 + 税额 = 价税合计、开票日期（不能晚于今天，超过一年提醒）、购买方是不是本公司、
**重复文件**（SHA-256）、**重复发票号**（本平台已确认 / 已用的，加上业务系统里已报销的）、
供应商（同一个税号以前对应的销售方名称不同时提醒）。

图片 OCR 走现有的视觉模型，受数据外发策略约束；文件只用来识别，不保存。

## 费用标准（`expense_policy_rule`，后台 → 费用标准）

结构化规则，不写进提示词：类别、城市等级、职级、单笔上限、是否必须有发票、超标后谁审批、生效期。
条件为空表示不限，同类多条时条件最具体的优先。员工职级：部门负责人按 manager，其他按 staff。

报销保存时检查：规定要发票的没有发票不能保存；超过上限必须填写**超标准说明**，说明和需要的审批级别写进明细说明，审批人能看到。
引用的发票必须已确认、没用过，报销金额不能超过发票金额；保存成功后发票记为已使用。
（重复发票号、预算不足、同时审批不透支预算——业务系统里已有，见 Java `FinanceService`：提交时查预算、批准时锁预算行。）

## ERP 推送（`service/erp_connector.py`）

已入账（POSTED）的凭证可以推送到 ERP（通用 Webhook）。只有财务部门人员能推送（和记账凭证同一个权限）。
**幂等**：`erp_export.voucher_id` 唯一，请求头 `Idempotency-Key: voucher-{id}` 固定；推送成功后再点直接返回原结果；
两个人同时点只有一个真的发出去；失败可以重试，用的还是同一个幂等键。请求体用 `ERP_WEBHOOK_SECRET` 做 HMAC-SHA256 签名（`X-Signature`）。

配置：`ERP_WEBHOOK_URL`、`ERP_WEBHOOK_SECRET`、`ERP_TIMEOUT_SECONDS`（默认 15）。

## IT 自助（`service/it_self_service.py`）

员工提工单前点“先找找自助办法”→ 推荐知识文章 → 明确选择 **[已解决]** 或 **[没有解决，创建工单]**。

- 只打开看过文章**不算**解决；只有点了“已解决”才计入自助解决率；
- 转出的工单号记在自助会话上；
- **重新打开**：点了“已解决”，7 天内同一个问题又来报修（同类且推荐文章有重叠或描述明显相似——只看分类不够，
  “忘记密码”和“VPN 连不上”都是故障），或者转出的工单被重开。重新打开的不算真正解决，也会拉低推荐它的文章的解决率；
- 指标（IT 部门 → 汇总）：知识推荐次数、明确确认解决、转工单、自助解决率、重新打开率、每篇文章的推荐 / 看过 / 解决 / 评价；
- 推荐 ≥ 5 次且解决率 < 30%，或评价 ≥ 3 次且有用 < 50% 的文章进入维护清单，每天提醒 IT 部门负责人（提醒规则 `it_kb_maintenance`）。

“打开文章”和“评价”是前端同时发出的两个请求，反馈用一条 `INSERT ... ON DUPLICATE KEY UPDATE` 写入，不会撞唯一约束。

测试：`tests/test_finance_it_extras.py`。
