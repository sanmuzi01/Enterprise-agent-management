# 面试演示脚本（5–8 分钟）

> 一句话定位：**把 AI 做成“能读业务数据、生成成果、推动流程、统计效果”的部门数字员工**，而不是又一个聊天窗口。
> 所有数字来自真实的 MySQL + Java 业务服务；AI 整理在演示环境用“离线演示模型”（规则抽取，不联网），讲清楚这一点本身就是加分项。

## 0. 开场前（2 分钟，提前做）

```powershell
.venv\Scripts\python.exe scripts\demo.py start      # 迁移 → 起 Java 业务服务/后端/前端 → 首次灌演示数据 → 打印就绪检查
.venv\Scripts\python.exe scripts\demo_walkthrough.py # 彩排：按下面的脚本自动走一遍，失败会指出是哪一步
```

- 就绪检查应全绿（“AI 模型”一项是黄色“!”，说明在用离线演示模型，正常）。
- 想要干净的初始状态：`scripts\demo.py reset`。演示后：`scripts\demo.py stop`。
- **现场出问题的兜底**：打开 `docs/demo-backup/index.html`，是同一条路线的带说明截图（图文备份），按顺序讲即可。
- 所有演示账号密码：`Demo@12345`。浏览器开多个无痕窗口分别登录，切角色不用反复登出。

| 账号 | 角色 | 用在哪一步 |
|---|---|---|
| `demo_emp` | 销售员工 | 一段话办多件事、提工单 |
| `demo_head` | 销售部负责人 | 审批 |
| `demo_fin` | 财务专员 | 核对记账凭证 |
| `demo_it` | IT 工程师 | 工单队列与 SLA |
| `demo_hr` | 人事专员 | 入转调离 |
| `demo_owner` | 企业所有者 | 落实调岗/离职变更 |

## 1. 为什么不是聊天机器人（30 秒）

“企业里 AI 落地的难点不是回答问题，而是**写入业务系统时不出错、出了事能追溯、效果能量化**。所以我的设计原则是三条：AI 只**生成草稿**；**人工核对后**才写入；每一步都有**权限、审计和指标**。”

## 2. 员工：一段话办多件事（2 分钟）— `demo_emp`

1. 登录直接落在**自己的部门工作台**（不是通用聊天页）；概览卡片按部门和身份变化。
2. 在“跨部门协同办理”里粘贴：

   > 上周五出差高铁票 260 元，发票号 G8891；出租车 48 元，暂无发票。另外我的笔记本电脑蓝屏了，需要报修，整个组都等着用

3. 点“拆分成步骤”：自动拆成 **报销** + **IT 工单** 两步，每步写明命中了哪些词、归哪个部门处理——**拆分是确定性规则，可解释，拆错能改**。
4. 对报销点“开始整理”：金额、发票号都带**原文依据**；“业务系统核对”读真实预算，提示“1 条费用没有发票号”。**勾选“我已核对”才能保存为草稿**——AI 不能直接写业务系统。
5. IT 工单：“整个组都等着用”被识别为影响范围大，建议**紧急**；核对页还会给自助排查建议、查重。

> 讲点：证据链（每个字段对应原文）、人工核对门槛、幂等（重复保存不会产生第二张单）。

## 3. 负责人与财务：审批 → 自动记账（1.5 分钟）— `demo_head`、`demo_fin`

1. `demo_head`：“待我审批”卡片汇总请假、报销、IT 申请、人事事项；**批准报销的同一事务里自动生成记账凭证草稿**。
2. `demo_fin` 打开“财务记账”：凭证带**科目建议 + 依据 + 置信度**（规则确定 / 推断 / 低置信）；风险逐项说明（无发票、业务招待费、大额、重复发票…）。
3. 有风险时必须勾选“已核对风险项”才能入账；**申请人不能确认自己报销单的凭证**（制单与复核分离）。

> 讲点：确定性规则 + 可追溯；系统只“建议”，不替人决定入账。

## 4. IT 服务台：SLA 与效果指标（1 分钟）— `demo_it`

1. 队列按**处理时限**排序，最急在前；接单 → 等待用户（SLA 暂停）→ 解决，全部留痕。
2. “汇总”页：SLA 达成率、平均首次响应、平均解决耗时、处理人负载。

> 讲点：**可量化的效率证据**，不是“感觉变快了”。

## 5. 人事入转调离：跨部门编排（1 分钟）— `demo_hr`

打开“入职办理”：自动生成**人事 / IT / 财务 / 负责人 / 员工**各自的办理清单，必办项全部完成且检查无阻断才能办结；离职时设备没收回、报销没结清**直接不能办结**。
（回到 `demo_fin` 的首页能看到“我的人事办理任务”——跨部门任务各归各的。）

## 6. 安全与可靠（30 秒，按追问展开）

- 权限在**后端强制**，前端隐藏只是体验：直接请求接口也会被拒（有专门的越权测试）。
- 企业成员被停用，所有部门权限**立即**失效。
- 写业务系统走签名 + 幂等：重复提交、响应丢失都不会产生重复单据。
- `scripts\demo.py status` / 管理后台“诊断”页有**运行就绪检查**，哪个环节没起来、怎么处理一目了然。

## 常见追问

| 问题 | 回答要点 |
|---|---|
| AI 整理的质量如何保证？ | 输出必须通过 schema 校验，每个依据必须是原文逐字片段，拿不准的进“疑点”；真实模型下还有人工核对门槛。离线演示模型是规则抽取，明确不冒充大模型。 |
| 为什么拆分不用大模型？ | 要可解释、可测试、零成本；拆错可手动改。后续可以换成模型拆分，接口不变。 |
| 怎么证明提升了效率？ | 管理后台有“AI 工作成果”指标（处理数、采纳率、修改率、节省工时=基准分钟×已保存数，基准可调）；IT 服务台有 SLA 与响应/解决耗时。 |
| 没做什么？ | 红字冲销/期间关账、按工作日历的 SLA、工单附件、考勤打卡、文件（PDF/图片）识别——文档里都写了边界。 |
| 部署？ | MySQL + Java 业务服务 + FastAPI + 前端；迁移走 Alembic/Flyway；见 docs/deployment.md。 |
